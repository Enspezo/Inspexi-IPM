# B-101 — INSPECTEUR kan een document ondertekenen namens élke rol (ook "Opdrachtgever" en "Beoordelaar"); rolcode wordt niet gevalideerd

- **Testgeval:** SEC-06 (sub c/d/e)
- **Actor / rol:** Inspecteur / INSPECTEUR (`inspecteur@inspexi-demo.nl`)
- **App:** API (:3001) · org: inspexidemo
- **Severity:** S1 (blokkerend — autorisatie-omzeiling, vier-ogen-principe en handtekeningintegriteit)
- **Type:** autorisatie / ontbrekende validatie
- **Datum/tijd:** 2026-07-27 08:20

## Verwacht
Ondertekenen is een handeling die aan een persoon én aan een rol gebonden hoort te zijn. Verwacht:
- een INSPECTEUR kan hooguit de rol `INSPECTOR` zetten, en alleen als er voor hem een ondertekenverzoek openstaat;
- ondertekenen namens `CLIENT` (opdrachtgever) of `REVIEWER` (beoordelaar) → 403;
- een onbekende `signerRoleCode` → 400 (moet bestaan in `imp_signer_roles`).

## Werkelijk
`POST /generated-documents/:id/sign` staat open voor `ALL_STAFF` en de service doet géén enkele controle op de meegegeven `signerRoleCode`:
- INSPECTEUR ondertekent als **`CLIENT`** → **201**, handtekening `status = SIGNED`, `signerName` volledig vrij te kiezen ("SEC06 Vervalste Klant");
- INSPECTEUR ondertekent als **`REVIEWER`** → **201** — de vier-ogen-rol wordt door de uitvoerder zelf gezet;
- INSPECTEUR ondertekent met de niet-bestaande rolcode **`BESTAAT-NIET`** → **201**; er is geen FK en geen lookup naar `imp_signer_roles`.

Het document had al een openstaande `CLIENT`-handtekening (`status = PENDING`, "Demo Klant"). De service werkt die rij niet bij maar maakt een **tweede** `CLIENT`-rij aan met `status = SIGNED` — het document telt daarna twee opdrachtgever-handtekeningen, waarvan één vervalst.

## Bewijs
- HTTP: `POST /generated-documents/:id/sign` (CLIENT) → **201**
  ```json
  {"success":true,"data":{"id":"dcf3bc72-42cc-4557-a665-5460d7b30d57",
   "generatedDocumentId":"563400a1-4de7-492c-9268-7ebb4a5dae48",
   "signerRoleCode":"CLIENT","signerName":"SEC06 Vervalste Klant",
   "signerEmail":"inspecteur@inspexi-demo.nl","signedAt":"2026-07-27T06:47:24.245Z", ... }}
  ```
- HTTP: idem met `"signerRoleCode":"REVIEWER"` → **201** (`id: eae5e27d-…`)
- HTTP: idem met `"signerRoleCode":"BESTAAT-NIET"` → **201** (`id: cdc60232-…`)
- DB na stap 2 (`imp_document_signatures` voor dit document):
  ```
   signer_role | signer_name           | signer_email               | status
   INSPECTOR   | Tom Visser            |                            | SIGNED
   CLIENT      | Demo Klant            |                            | PENDING
   CLIENT      | SEC06 Vervalste Klant | inspecteur@inspexi-demo.nl | SIGNED   <-- vervalst
  ```
- Cross-tenant is wél dicht: dezelfde call op een document van `inspexicompleet` → 403 `"Document hoort niet bij uw organisatie"`.

## Analyse / vermoedelijke oorzaak
`generated-documents.controller.ts` zet `@Roles(...STAFF)` (= `ALL_STAFF`) op `POST generated-documents/:id/sign`.
`DocumentSigningService.signDocument()` (`document-signing.service.ts:81`) controleert alleen of het document niet `FINALIZED` is en doet daarna direct een `documentSignature.create({ signerRoleCode: dto.signerRoleCode, … })`:

```ts
async signDocument(id: string, user: User, dto: SignDocumentDto) {
  const doc = await this.documents.findById(id, user);
  if (doc.status === GeneratedDocumentStatus.FINALIZED) { throw new BadRequestException(...); }
  const sig = await this.prisma.documentSignature.create({ data: { ..., signerRoleCode: dto.signerRoleCode, ... } });
```

Er is dus (a) geen koppeling tussen gebruikersrol en `signerRoleCode`, (b) geen controle op een openstaand `REQUESTED`-verzoek voor deze gebruiker, en (c) geen validatie tegen `imp_signer_roles` (de kolom `signer_role` is vrije `text`, geen FK). De publieke variant (`signViaRequest`) is wél aan een verzoek gebonden — alleen de interne route niet.

## Advies
1. Beperk `POST /generated-documents/:id/sign` tot de rollen die intern mogen tekenen, en map de gebruikersrol op toegestane `signerRoleCode`-waarden (INSPECTEUR → alleen `INSPECTOR`; REVIEW_ROLES → `REVIEWER`).
2. `CLIENT` en `INSTALLATION_RESPONSIBLE` mogen alléén via de publieke ondertekenlink (`signature-requests/:requestId/sign`) worden gezet — nooit door staf.
3. Valideer `signerRoleCode` tegen `imp_signer_roles` (lookup + duidelijke 400), of maak er een echte FK van.
4. Update in plaats van insert: koppel de handtekening aan de bestaande `REQUESTED`/`PENDING`-rij en weiger een tweede SIGNED-rij voor dezelfde rol (`@@unique([generatedDocumentId, signerRole])`).
5. Leg `signedIpAddress` en de ondertekenende `userId` vast (nu leeg) voor herleidbaarheid.
