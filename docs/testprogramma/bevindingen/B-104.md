# B-104 — Inhoud van een reeds ondertekend document is nog te herschrijven; de handtekening blijft geldig staan

- **Testgeval:** SEC-06 (aanvullend, EXTRA-05)
- **Actor / rol:** Inspecteur / INSPECTEUR (`inspecteur@inspexi-demo.nl`)
- **App:** API (:3001) · org: inspexidemo
- **Severity:** S2 (ernstig — handtekening dekt niet langer de inhoud; compliance-risico)
- **Type:** business-gate ontbreekt / integriteit
- **Datum/tijd:** 2026-07-27 08:45

## Verwacht
Zodra er één geldige handtekening (`SignatureStatus.SIGNED`) onder een document staat, hoort de inhoud bevroren te zijn. Een poging tot bewerken zou **400/403** moeten geven ("document is al ondertekend"), of op zijn minst alle bestaande handtekeningen moeten invalideren en de status terugzetten.

## Werkelijk
`PATCH /generated-documents/:id` met een `editedContent` slaagt gewoon op een document met `status = PENDING_SIGNATURES` waarop al een `INSPECTOR`-handtekening met `status = SIGNED` staat (Tom Visser, 2026-06-15). Resultaat: **HTTP 200**, `is_edited = true`, `edited_content` volledig vervangen door de aangeleverde HTML. De handtekening blijft ongewijzigd `SIGNED` en de documentstatus blijft `PENDING_SIGNATURES`.

Omdat de renderer bij preview/PDF-export `editedContent` gebruikt zodra `isEdited` waar is (`contentOf()`), levert het systeem daarna een PDF met **nieuwe inhoud onder een oude handtekening**. Alleen `FINALIZED`-documenten zijn beschermd tegen ondertekenen; tegen *bewerken* is zelfs die status niet gecontroleerd in de update-route.

Combinatie met B-101/B-103: dezelfde INSPECTEUR mag ook zelf genereren en zelf namens de opdrachtgever tekenen — de volledige keten "genereren → laten tekenen → inhoud vervangen" is voor één rol beschikbaar.

## Reproductie
```bash
TOKEN=$(curl -s -X POST -H 'Host: inspexidemo.localhost' -H 'Content-Type: application/json' \
  -d '{"email":"inspecteur@inspexi-demo.nl","password":"Password123!"}' \
  http://localhost:3001/api/v1/auth/login | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"]["accessToken"])')

# document 563400a1 heeft status PENDING_SIGNATURES en een SIGNED INSPECTOR-handtekening
curl -i -X PATCH -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"editedContent":"<h1>SEC06 GEMANIPULEERD RAPPORT</h1>"}' \
  http://localhost:3001/api/v1/generated-documents/563400a1-4de7-492c-9268-7ebb4a5dae48
```

## Bewijs
- HTTP: `PATCH /generated-documents/563400a1-…` → **200**, body bevat het bijgewerkte document
- DB direct na de call:
  ```
   id        | status             | is_edited | edited
   563400a1… | PENDING_SIGNATURES | t         | <h1>SEC06 GEMANIPULEERD RAPPORT</h1>
  ```
  en `imp_document_signatures` ongewijzigd: `INSPECTOR | Tom Visser | SIGNED | 2026-06-15 10:00:00`
- Geen waarschuwing, geen statuswijziging, geen invalidatie van de handtekening.

> Teruggedraaid met psql (`is_edited=false, edited_content=NULL, edited_by=NULL, edited_at=NULL`).

## Analyse / vermoedelijke oorzaak
`generated-documents.controller.ts` → `@Patch('generated-documents/:id') @Roles(...STAFF)` en `GeneratedDocumentsService.update()` schrijft `editedContent`/`isEdited` weg zonder statuscontrole. De guard die wél bestaat zit alleen in `signDocument()` (`FINALIZED` → 400) en in `delete()` (`FINALIZED` → 403); de update-route kent die controle niet, en géén van de routes kijkt naar het bestaan van `SIGNED`-handtekeningen.

`generatePreview()`/`exportPdf()` gebruiken `contentOf(doc)` = `doc.isEdited && doc.editedContent ? doc.editedContent : doc.htmlContent`, waarna `injectSignaturesIntoHtml()` de bestaande handtekeningen onder de gewijzigde inhoud plakt.

## Advies
1. Weiger `PATCH` (en elke inhoudswijziging) zodra er minimaal één `SignatureStatus.SIGNED` bij het document hoort → 400 met NL-melding, bijv. "Dit document is al ondertekend en kan niet meer gewijzigd worden".
2. Weiger `PATCH` óók op `FINALIZED` (nu niet gecontroleerd).
3. Als bewerken na ondertekening toch een geldige workflow is: zet alle handtekeningen terug naar `PENDING`/`INVALIDATED`, zet de status terug naar `DRAFT` en informeer de ondertekenaars — nooit stilzwijgend.
4. Leg een inhouds-hash vast bij het ondertekenen (`signedContentHash`) en toon bij preview/PDF een waarschuwing als de huidige inhoud daarvan afwijkt.

## Status
**Opgelost** (WP-A3, PR `fix/wp-a3-document-chain`). Twee lagen:
- **Al eerder deels gefixt (SYNC-5, vóór dit werkpakket):** `updateEditedContent()` blokkeerde inmiddels documenten met status `SIGNED` of `FINALIZED` (403). Die check keek echter alleen naar de **documentstatus**: bij `PENDING_SIGNATURES` met een reeds gezette `SIGNED`-handtekeningrij (het scenario uit deze bevinding) kon bewerken nog steeds.
- **Nu (WP-A3):** de poort is een handtekeningcheck — `FINALIZED`, status `SIGNED` óf ≥1 `SIGNED`-handtekeningrij → **403** "Een ondertekend document kan niet meer bewerkt worden".
- **Portal:** de staf-portal (Beheer) heeft géén inhouds-editor — `PATCH /generated-documents/:id` wordt daar nergens aangeroepen, dus er is portal-zijdig niets read-only te maken. De editor leeft in de PWA (`../Inspexi-App`); die toont bij een bewerkpoging na de eerste handtekening voortaan de 403-melding van de API (de API-block is leidend). PWA-zijdige UX (knop verbergen) is een restpunt voor de PWA-repo.
- **Restpunt (advies 4, buiten scope):** een inhouds-hash bij ondertekening (`signedContentHash`) + waarschuwing bij afwijking is niet geïmplementeerd.

Regressietests: unit (`generated-documents.service.spec.ts`: SIGNED-rij bij PENDING_SIGNATURES → 403) + e2e (`test/generated-documents-roles.e2e-spec.ts`: PATCH na eerste handtekening → 403).
