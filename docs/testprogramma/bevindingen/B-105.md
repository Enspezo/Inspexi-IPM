# B-105 — Cross-tenant resources geven 403 i.p.v. 404: het bestaan van andermans records is af te leiden (existence-oracle)

- **Testgeval:** SEC-07
- **Actor / rol:** Org-beheerder / ORG_ADMIN (`admin@inspexi-demo.nl`, org A `inspexidemo`)
- **App:** API (:3001) · doelwit: org B `testbedrijf` en org C `inspexicompleet`
- **Severity:** S3 (matig — informatielek van bestaan/id's; géén inhoudelijke data gelekt)
- **Type:** inconsistente statuscode / informatiedisclosure
- **Datum/tijd:** 2026-07-27 08:38

## Verwacht
Volgens het masterplan (§3 orakels) en SEC-07: een resource van een andere organisatie moet **404** geven — "bestaan niet onthullen". De respons voor "bestaat niet" en "bestaat, maar hoort bij een andere org" moet ononderscheidbaar zijn.

## Werkelijk
Het gedrag is per module verschillend. Met een geldig org A-token op het eigen subdomein:

| Endpoint | UUID van een andere org | Niet-bestaande UUID | Oordeel |
|---|---|---|---|
| `GET /contacts/:id` | **403** `"Forbidden"` | 404 `"Relatie niet gevonden"` | lek |
| `GET /quotes/:id` | **403** `"Forbidden"` | 404 `"Offerte niet gevonden"` | lek |
| `GET /users/:id` | **403** `"Forbidden"` | 404 `"Gebruiker niet gevonden"` | lek |
| `GET /organizations/:id` | **403** `"Geen toegang tot deze organisatie"` | 404 | lek |
| `GET /generated-documents/:id` | **403** `"Document hoort niet bij uw organisatie"` | 404 | lek |
| `GET /inspection-plans/:id` | 404 `"Inspectieplan niet gevonden"` | 404 | **correct** |
| `GET /tasks/:id` | 404 `"Taak niet gevonden"` | 404 | correct |

Het verschil 403↔404 is een betrouwbaar orakel: wie een UUID heeft (uit een e-mail, logregel, gedeelde link of gewoon door te raden binnen een gelekte lijst) kan vaststellen dat die id **bestaat en bij een andere organisatie hoort**. De 403-melding van `/organizations/:id` en `/generated-documents/:id` bevestigt dat zelfs letterlijk in tekst.

Inhoudelijke data lekt níet: in geen enkel geval kwam er veldinhoud van de andere org terug, en alle cross-tenant mutaties (`PATCH /contacts/:id`, `DELETE /contacts/:id`, `PATCH /users/:id`, `PATCH /quotes/:id`) werden geweigerd met de doelrecords ongewijzigd in de DB. Daarom S3 en niet S1.

## Reproductie
```bash
TOKEN=$(curl -s -X POST -H 'Host: inspexidemo.localhost' -H 'Content-Type: application/json' \
  -d '{"email":"admin@inspexi-demo.nl","password":"Password123!"}' \
  http://localhost:3001/api/v1/auth/login | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"]["accessToken"])')

# (1) bestaand contact van org B (testbedrijf)  -> 403
curl -i -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $TOKEN" \
  http://localhost:3001/api/v1/contacts/5017f2a8-b7a8-4166-82fd-bad3c64e4818

# (2) niet-bestaande UUID                        -> 404
curl -i -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $TOKEN" \
  http://localhost:3001/api/v1/contacts/00000000-0000-4000-8000-000000000000

# (3) inspectieplan van org C = referentiegedrag  -> 404 (correct)
curl -i -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $TOKEN" \
  http://localhost:3001/api/v1/inspection-plans/d22a5cbd-acf3-41e3-b760-2fde728d51ac
```

## Bewijs
- (1) → **403** `{"success":false,"message":"Forbidden","statusCode":403}`
- (2) → **404** `{"success":false,"message":"Relatie niet gevonden","statusCode":404}`
- (3) → **404** `{"success":false,"message":"Inspectieplan niet gevonden","statusCode":404}`
- `GET /quotes/<org C offerte>` → 403 `"Forbidden"` vs. `GET /quotes/<random UUID>` → 404 `"Offerte niet gevonden"`
- `GET /users/<org B user>` → 403 `"Forbidden"` vs. random UUID → 404 `"Gebruiker niet gevonden"`
- `GET /organizations/<org B>` → 403 `"Geen toegang tot deze organisatie"`
- Data-integriteit gecontroleerd na alle cross-tenant mutatiepogingen (psql): `company_name` = "Installatie Groep Nederland", `first_name` = "Lisa", offerte-subject ongewijzigd — niets aangepast.

## Analyse / vermoedelijke oorzaak
Twee patronen naast elkaar in de codebase:
- **Correct**: `assertFound(...)` / een `findFirst` mét `orgId` in de `where` → de org-scope zit in de query, dus een vreemde id komt simpelweg niet terug → 404.
- **Lekkend**: eerst `findUnique({ where: { id } })` en daarna een aparte org-vergelijking die een kale `ForbiddenException()` gooit. Nest vult dan zelf de Engelse boodschap `"Forbidden"` in.

Het lekkende patroon staat op ~20 plaatsen, o.a.:
`modules/contacts/contacts.service.ts:155`, `contact-persons.service.ts:152/228`, `locations.service.ts:231/257/357/456/507/535/551`,
`modules/quotes/quotes.helpers.ts:173` (`findQuoteForUser`), `quotes.service.ts:529/558`, `quote-pdf.service.ts:38`,
`modules/products/products.service.ts:74`, `quote-templates/quote-templates.service.ts:123`, `email-templates/email-templates.service.ts:74`,
`customer-groups/customer-groups.service.ts:74`, `requests/requests.service.ts:170/287`.

Let op het onderscheid met **SEC-08**: bij FK-injectie is een 403 met een expliciete NL-melding ("Relatie hoort niet bij uw organisatie") juist gewenst en correct — daar geeft de aanvaller de id zelf op als *invoer* voor een eigen record. Deze bevinding gaat uitsluitend over het *ophalen/muteren van andermans resource op de id-route*.

## Advies
1. Kies één norm en leg die vast: cross-tenant lookups op `/:id`-routes geven **404** met dezelfde melding als "niet gevonden".
2. Vervang het patroon `findUnique(id)` + org-check door een org-gescopete query (`findFirst({ where: { id, ...orgScope(user) } })` + `assertFound(...)`), consistent met `inspection-plans` en `tasks`. Dat maakt en passant de meldingen Nederlands (zie B-106).
3. Voeg een E2E-regressietest toe die per module het paar (vreemde-org-id, niet-bestaande-id) vergelijkt en faalt zodra de statuscodes verschillen — `test/cross-tenant.e2e-spec.ts` dekt nu wel de FK-injectie maar niet dit id-route-gedrag.
