# B-106 — Autorisatie- en authenticatiefouten geven Engelse meldingen ("Forbidden resource", "Forbidden", "Unauthorized")

- **Testgeval:** SEC-01 t/m SEC-07 (systematisch), aanvullend EXTRA-01/02
- **Actor / rol:** alle rollen (ORG_ADMIN, MANAGER, BACKOFFICE, WERKVOORBEREIDER, INSPECTEUR)
- **App:** API (:3001) → doorwerkend in portal (:5173) en client-portal (:5174) · org: inspexidemo
- **Severity:** S3 (matig — verwarrende UX, orakel "NL-foutmelding" niet gehaald)
- **Type:** foutafhandeling / i18n
- **Datum/tijd:** 2026-07-27 08:50

## Verwacht
Masterplan §3 (orakel): "Foutmelding is **in het Nederlands**, begrijpelijk, en bij het juiste veld." De bevindingen-template noemt "Engelse foutmelding" expliciet als S3. Verwacht dus bij een 401/403 een Nederlandse melding, zoals de rest van het domein die wél levert.

## Werkelijk
Alle 403's die uit de globale `RolesGuard` komen geven de Nest-default **`"Forbidden resource"`**, en alle 401's uit de `JwtAuthGuard` geven **`"Unauthorized"`**. De kale `ForbiddenException()`-aanroepen in de servicelaag (zie B-105) geven **`"Forbidden"`**. Dat is inconsistent met de domeinlaag, die juist keurig Nederlands is.

Voorbeelden uit deze run — Engels:
- `GET /organizations` (ORG_ADMIN) → `{"success":false,"message":"Forbidden resource","statusCode":403}`
- `POST /norm-types` (ORG_ADMIN) → `"Forbidden resource"`
- `PATCH /contacts/:id` (INSPECTEUR) → `"Forbidden resource"`
- `POST /quotes/:id/approve` (BACKOFFICE) → `"Forbidden resource"`
- `GET /organizations/:id` (WERKVOORBEREIDER) → `"Forbidden resource"`
- `POST /generated-documents/:id/finalize` (INSPECTEUR) → `"Forbidden resource"`
- `GET /contacts/<org B id>` → `"Forbidden"`
- Geen/onzin-token → `"Unauthorized"`

Diezelfde run laat zien hoe het wél hoort — Nederlands, en zelfs met de reden erbij:
- `"U heeft niet de vereiste rol om dit verzoek goed te keuren"` (offerte-goedkeuring, SEC-04)
- `"U heeft geen toegang tot deze organisatie"` (TenantGuard, SEC-09)
- `"Gebruik het subdomein van uw organisatie om in te loggen"` (SEC-09)
- `"Uw account hoort niet bij deze organisatie"` (login-realm, SEC-09)
- `"Relatie hoort niet bij uw organisatie"`, `"Inspecteur hoort niet bij uw organisatie"` (FK-validatie, SEC-08)
- `"Document hoort niet bij uw organisatie"` (generated-documents)

De gebruiker ziet dus afhankelijk van de route willekeurig Nederlands of Engels — en de Engelse variant zegt bovendien niets over wat er nu eigenlijk mis is (rol? organisatie? plan/feature?).

## Reproductie
```bash
TOKEN=$(curl -s -X POST -H 'Host: inspexidemo.localhost' -H 'Content-Type: application/json' \
  -d '{"email":"admin@inspexi-demo.nl","password":"Password123!"}' \
  http://localhost:3001/api/v1/auth/login | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"]["accessToken"])')

# RolesGuard-403 (Engels)
curl -i -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $TOKEN" \
  http://localhost:3001/api/v1/organizations

# TenantGuard-403 op hetzelfde token (Nederlands) — ter vergelijking
curl -i -H 'Host: testbedrijf.localhost' -H "Authorization: Bearer $TOKEN" \
  http://localhost:3001/api/v1/contacts

# JwtAuthGuard-401 (Engels)
curl -i -H 'Host: inspexidemo.localhost' http://localhost:3001/api/v1/contacts
```

## Bewijs
- `GET /organizations` → **403** `{"success":false,"message":"Forbidden resource","statusCode":403}`
- `GET /contacts` op vreemd subdomein → **403** `{"success":false,"message":"U heeft geen toegang tot deze organisatie","statusCode":403}`
- `GET /contacts` zonder token → **401** `{"success":false,"message":"Unauthorized","statusCode":401}`
- Zelfde patroon waargenomen op alle ~20 rol-403's in SEC-01 t/m SEC-06.

## Analyse / vermoedelijke oorzaak
`RolesGuard` gooit een `ForbiddenException` zonder message-argument, waarna NestJS de standaardtekst `"Forbidden resource"` invult; `AuthGuard('jwt')` doet hetzelfde met `"Unauthorized"`. De globale exception-filter geeft `exception.message` ongewijzigd door aan het `{ success:false, message }`-envelope, dus de Engelse default belandt rechtstreeks in de UI. In de servicelaag zorgen de kale `new ForbiddenException()`-aanroepen (B-105) voor dezelfde situatie met `"Forbidden"`.

## Advies
1. Geef `RolesGuard` een NL-melding, bij voorkeur met context: "U heeft niet de juiste rol voor deze actie."
2. Geef `JwtAuthGuard` (`handleRequest`) een NL-melding: "Uw sessie is verlopen of u bent niet ingelogd."
3. Vervang de kale `new ForbiddenException()`-aanroepen door een boodschap (of, beter, door een org-gescopete query met 404 — zie B-105).
4. Vang als vangnet in de globale exception-filter de Engelse Nest-defaults (`Forbidden resource`, `Forbidden`, `Unauthorized`, `Internal server error`) af en map ze op Nederlandse standaardteksten, zodat er nooit meer Engels doorlekt.
