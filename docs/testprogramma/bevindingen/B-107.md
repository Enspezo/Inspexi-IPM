# B-107 — Afgewezen `POST /inspection-plans` laat toch een inspectieplan achter (niet-atomaire create)

- **Testgeval:** SEC-08 (sub h) — ontdekt bij de DB-nacontrole "geen kruis-koppeling"
- **Actor / rol:** Org-beheerder / ORG_ADMIN (`admin@inspexi-demo.nl`, org A `inspexidemo`)
- **App:** API (:3001) · org: inspexidemo
- **Severity:** S3 (matig — datavervuiling en misleidende foutrespons; geen cross-tenant lek)
- **Type:** transactionaliteit / partial write
- **Datum/tijd:** 2026-07-27 08:57

## Verwacht
Een create die met een foutstatus eindigt (404/400) hoort niets achter te laten: `POST /inspection-plans` met een ongeldige `scopeLocationIds` moet de hele aanmaak terugdraaien. De caller krijgt een fout en gaat er terecht van uit dat het plan niet bestaat.

## Werkelijk
`POST /inspection-plans` met een `scopeLocationIds` die naar een asset-node van een **andere organisatie** wijst geeft correct **404 `"Scope-locatie niet gevonden"`** — de scope-rij wordt inderdaad níet aangemaakt (isolatie is intact). Maar het **inspectieplan zelf is dan al weggeschreven** en blijft als weesrecord in `imp_inspection_plans` staan (`status = draft`, mét `contactId` en `locationId`, zonder scope).

Reproduceerbaar en niet beperkt tot cross-tenant: dezelfde partial write treedt op bij een volstrekt onbestaande scope-UUID. Drie pogingen → drie 404's → **drie plannen in de database**.

Gevolg: de gebruiker ziet een foutmelding, klikt opnieuw, en houdt bij elke poging een extra concept-plan over dat in de overzichtslijst opduikt. Bij een gevuld `referenceNumber` kan de tweede poging bovendien stuklopen op de per-org-uniciteit van het rapportnummer dat de eerste, "mislukte" poging al bezet heeft.

## Reproductie
```bash
TOKEN=$(curl -s -X POST -H 'Host: inspexidemo.localhost' -H 'Content-Type: application/json' \
  -d '{"email":"admin@inspexi-demo.nl","password":"Password123!"}' \
  http://localhost:3001/api/v1/auth/login | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"]["accessToken"])')

# scopeLocationIds = asset-node van org C (inspexicompleet)
curl -i -X POST -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"contactId":"186389ba-ea4f-4992-9ac0-2329c41a4d51",
       "locationId":"a973fa20-ce4a-4728-bbcf-6cb98a4ac7c2",
       "scopeLocationIds":["4a505b2f-1c01-42fe-8faa-a80b49402418"],
       "projectName":"SEC08 scope-injectie","normTypeCode":"NEN1010"}' \
  http://localhost:3001/api/v1/inspection-plans

# variant met een volstrekt onbestaande UUID → zelfde 404, zelfde weesrecord
#   "scopeLocationIds":["00000000-0000-4000-8000-000000000000"]

# controle in de database
psql -h localhost -p 5433 -U inspectie -d inspectie \
  -c "SELECT id, project_name, status FROM imp_inspection_plans WHERE project_name LIKE 'SEC08%';"
```

## Bewijs
- HTTP: `POST /inspection-plans` → **404** `{"success":false,"message":"Scope-locatie niet gevonden","statusCode":404}`
- DB na drie afgewezen pogingen:
  ```
   bff40a28-f408-4915-9666-a73efbb0df16 | SEC08 scope-injectie         | draft
   d9524928-50a7-47fd-b245-c233e0955524 | SEC08 scope-injectie HERHAAL | draft
   50ed9e96-86b0-4d59-86eb-972d56850465 | SEC08 scope-onbekend         | draft
  ```
- `imp_inspection_plan_locations` voor die plannen: **0 rijen** — de scope-koppeling is correct geweigerd, alleen de ouder bleef staan.
- Ter contrast: de andere SEC-08-injecties (`contactId`, `assignedTo`, `reviewerId`, `locationId` van een vreemde org) worden vóór het schrijven gevalideerd via `assertSameOrg` en laten wél niets achter (0 rijen `SEC08%` na afloop).

> De drie weesplannen zijn met psql opgeruimd.

## Analyse / vermoedelijke oorzaak
In `inspection-plans.service.ts` (`create()`, regels ~243-335) staat de FK-validatie netjes vóór de schrijfactie:
```ts
await Promise.all([ assertSameOrg(this.prisma.contact, dto.contactId, …), … ]);
…
const plan = await this.prisma.inspectionPlan.create({ data: { … } });   // ← commit
…
if (plan.locationId) {
  await this.assetNodes.ensureRootNode(plan.locationId, user);
  if (dto.scopeLocationIds?.length) {
    await this.replaceScopeLocations(plan.id, orgId, plan.locationId, dto.scopeLocationIds);  // ← throwt 404
  }
} else if (dto.scopeLocationIds?.length) {
  throw new BadRequestException('scopeLocationIds vereist een hoofdlocatie (locationId)');    // ← idem
}
```
`scopeLocationIds` (en de `locationId`-vereiste ervoor) worden dus pas ná de `create()` gevalideerd, en het geheel zit niet in een `$transaction`. Elke throw in dat blok laat het al gecommitte plan staan. Hetzelfde geldt voor de zij-effecten van `ensureRootNode()`, dat vóór de mislukte scope-validatie al een wortel-node kan aanmaken.

## Advies
1. Valideer `scopeLocationIds` (bestaan + org + "zit in de boom van `locationId`") **vóór** de `create()`, in hetzelfde `Promise.all`-blok als de andere `assertSameOrg`-checks — inclusief de regel "scope vereist een hoofdlocatie".
2. Wikkel plan-create + `ensureRootNode` + `replaceScopeLocations` in één `prisma.$transaction`, zodat een latere fout alles terugdraait.
3. Overweeg de statuscode: een door de client aangeleverde, niet-vindbare scope-id is invoervalidatie → **400** past beter dan 404 (nu lijkt het alsof de *route* niet bestaat).
4. Zelfde patroon controleren in `update()` en in andere services die na een `create()` nog validerende vervolgstappen doen.

## Status

**Opgelost in WP-C5** (branch `fix/wp-c5-config-validation`), conform advies 1+2+4:
- `create()`: de regel "scope vereist een hoofdlocatie" én de validatie van elke scope-node
  (`assertValidScopeLocation`: bestaan + org + juiste boom) staan nu in het
  `Promise.all`-validatieblok **vóór** elke schrijfactie.
- Plan-create + scope-rijen zitten in één **`prisma.$transaction`** — een latere fout draait
  het geheel terug. `ensureRootNode` draait bewust vóór (buiten) de transactie: de wortel-node
  is persistente, plan-onafhankelijke boomdata en de numbering-engine heeft eigen transacties
  met een P2002-retry die binnen een geaborteerde outer-tx zou stuklopen; een achtergebleven
  wortel-node is idempotent en onschadelijk.
- `update()` (advies 4): zelfde pre-write scope-validatie + update+scope in één transactie.
- Advies 3 (404→400 voor een niet-vindbare scope-id) is bewust NIET doorgevoerd: de 404 komt
  uit de gedeelde `assertFound`-conventie ("bestaat niet binnen uw org"), die overal in de
  API zo werkt — afwijken alleen hier zou inconsistent zijn.
- Tests: 3 unit (geen create-call bij afgekeurde scope; tx-write) + 2 e2e (weesplan-count 0).
