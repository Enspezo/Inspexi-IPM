# B-151 — Client-realm geeft 403 i.p.v. de voorgeschreven 404 bij een vreemde inspectie

- **Testgeval:** SEC-10
- **Actor / rol:** ClientUser (`klant@inspexi-demo.nl`) / client-realm
- **App:** API (:3001) · org: inspexidemo → probeert plannen van testbedrijf / inspexicompleet / inspexibasis
- **Severity:** S4 (cosmetisch — contractafwijking, géén informatielek)
- **Type:** statuscode-conventie
- **Datum/tijd:** 2026-07-27 08:44

## Verwacht
`docs/testprogramma/07-cross-tenant-security.md` SEC-10 schrijft **404** voor ("client-realm is org-gescoped"), en
`08-bevindingen-template.md` §Statuscodes-referentie zegt: *"Cross-tenant resource → **404** (bestaan niet onthullen)"*.
De staf-realm doet dit al zo: `GET /inspection-plans/<vreemd-id>` geeft 404 "Inspectieplan niet gevonden".

## Werkelijk
De client-realm geeft consequent **403 "Geen toegang tot deze inspectie"** — zowel voor een bestaand plan van een
andere org als voor een volledig niet-bestaande UUID. De isolatie zelf is dus in orde en er is **geen
enumeratie-oracle** (beide gevallen zijn niet van elkaar te onderscheiden), maar de statuscode wijkt af van de
gedocumenteerde conventie én van de staf-realm.

## Reproductie

```bash
# clienttoken van org A
CT=$(curl -s -X POST -H 'Host: inspexidemo.localhost' -H 'Content-Type: application/json' \
  -d '{"email":"klant@inspexi-demo.nl","password":"Password123!"}' \
  http://localhost:3001/api/v1/client/auth/login | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"]["accessToken"])')

# 1) eigen plan → 200
curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $CT" \
  http://localhost:3001/api/v1/client/inspections/cc495211-6b38-440c-b323-59e64a4c9af9

# 2) plan van org B (Test Bedrijf) → 403
curl -s -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $CT" \
  http://localhost:3001/api/v1/client/inspections/7b9348c5-5e58-480f-a45d-7db5ced61413

# 3) niet-bestaande UUID → identiek 403
curl -s -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $CT" \
  http://localhost:3001/api/v1/client/inspections/00000000-0000-4000-8000-000000000000
```

## Bewijs

```
# 1) eigen plan
HTTP 200

# 2) plan van org B
HTTP 403
{"success":false,"message":"Geen toegang tot deze inspectie","statusCode":403}

# 3) niet-bestaande UUID
HTTP 403
{"success":false,"message":"Geen toegang tot deze inspectie","statusCode":403}

# idem voor de sub-resources
GET /client/inspections/<vreemd>/findings   → 403 "Geen toegang tot deze inspectie"
GET /client/inspections/<vreemd>/documents  → 403 "Geen toegang tot deze inspectie"

# eigen plan op het subdomein van een andere org (host = testbedrijf.localhost)
GET /client/inspections/cc495211-…          → 403 "Geen toegang tot deze inspectie"
GET /client/inspections                     → 200 {"success":true,"data":[]}
```

## Analyse / vermoedelijke oorzaak
`apps/api/src/modules/client-inspections/client-inspections.service.ts`:

```ts
async assertInspectionAccess(clientUserId: string, orgId: string, planId: string): Promise<void> {
  if (!(await this.hasAccessToInspection(clientUserId, orgId, planId))) {
    throw new ForbiddenException('Geen toegang tot deze inspectie');
  }
}
```

`hasAccessToInspection()` doet één `findFirst` met `{ id: planId, orgId, deletedAt: null, OR: <toegangsscope> }`.
Er wordt bewust géén onderscheid gemaakt tussen "bestaat niet", "andere org" en "geen grant" — dat is de reden dat
er geen lek is. Alleen de gekozen exception is `Forbidden` waar het projectcontract `NotFound` voorschrijft.
Positief: `orgId` komt hier altijd uit `@CurrentTenant` (subdomein) en nooit uit het token — dat is de eigenlijke
isolatiegarantie en die is intact.

## Advies
Vervang `ForbiddenException('Geen toegang tot deze inspectie')` door
`NotFoundException('Inspectie niet gevonden')` in `assertInspectionAccess()` (en de gelijkaardige plek in
`client-documents`/`client-findings`/`client-messages`), zodat de client-realm dezelfde 404-conventie volgt als de
staf-realm. Laat `assertSignAccess()` wél 403 geven — daar is het bestaan van het plan al bevestigd en gaat het om
een ontbrekend *recht*, niet om zichtbaarheid. Werk daarna de client-portal-foutafhandeling bij (403 → 404).
Alternatief, als 403 bewust is: pas dan `07-cross-tenant-security.md` en de statuscode-referentie in
`08-bevindingen-template.md` aan zodat het contract klopt.
## Status
**Opgelost** in WP-C1 (branch `fix/wp-c1-error-contract`).
`assertInspectionAccess()` in `client-inspections.service.ts` gooit nu
`NotFoundException('Inspectie niet gevonden')` — alle sub-services (client-documents,
-findings, -messages, -requests, -repair) delegeren hiernaartoe, dus de hele client-realm
volgt de 404-conventie. `assertSignAccess()` blijft bewust 403 ("Geen recht om dit document
te ondertekenen"): daar is het bestaan al bevestigd en ontbreekt alleen het recht. De
client-portal-foutafhandeling toont de `message` generiek en had geen statuscode-specifieke
403-tak voor deze routes (gecontroleerd). E2e bijgewerkt: `client-portal.e2e-spec.ts`
(cross-tenant plandetail → 404).
