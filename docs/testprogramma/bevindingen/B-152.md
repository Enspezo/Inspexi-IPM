# B-152 — Publieke offerte-token is niet aan de tenant gebonden: lezen én ondertekenen lukt vanaf elk subdomein

- **Testgeval:** SEC-11
- **Actor / rol:** Anonieme bezoeker (publieke route, geen auth)
- **App:** API (:3001) · offerte van org `inspexidemo`, benaderd via `inspexicompleet.localhost` en `mijn.localhost`
- **Severity:** S2 (ernstig — tenantgrens niet afgedwongen op een statuswijzigend publiek endpoint)
- **Type:** cross-tenant isolatie / entitlement-gate op de verkeerde org
- **Datum/tijd:** 2026-07-27 08:46

## Verwacht
SEC-11: *"Token bindt aan eigen org; geen kruislek."* Een publieke offerte-token hoort alleen te resolven binnen het
subdomein van de organisatie die de offerte bezit. Op een vreemd subdomein hoort de offerte niet gevonden te worden
(404), en zeker niet ondertekend te kunnen worden.

## Werkelijk
De publieke offerte-routes negeren de tenantcontext volledig. `QuotePublicService.findByPublicToken()` doet een
`findUnique({ where: { publicToken } })` **zonder `orgId`-filter en zonder vergelijking met `req.tenant`**. Gevolgen:

1. **Lezen kruislings** — een offerte van org A wordt volledig geserveerd op het subdomein van org B, inclusief
   `organization` (naam/logo/huisstijlkleur van org A) en het e-mailadres van de klantcontact.
2. **Statuswijzigende acties kruislings** — `POST /public/quotes/:token/sign` slaagt vanaf een vreemd subdomein.
   De offerte gaat naar `GEACCEPTEERD`, `signedAt`/`clientName`/`clientIp` worden gezet, er worden notificaties in
   org A aangemaakt en er wordt automatisch een **project in org A** aangemaakt. Dezelfde ongebondenheid geldt voor
   `GET :token/pdf`, `POST :token/questions` en `GET :token/attachments/:id/download`.
3. **Entitlement-gate tegen de verkeerde org** — `@RequiresFeature('CRM_COMPLEET')` staat op de
   `PublicQuotesController` en wordt geëvalueerd tegen de **bezoekende** tenant, niet tegen de eigenaar van de
   offerte. Daardoor geeft dezelfde geldige token 200 op `inspexicompleet`/`mijn` en 403 `FEATURE_NOT_IN_PLAN` op
   `testbedrijf`/`inspexibasis` — de gate zegt dus niets over het abonnement van de org die de offerte verstuurde.

## Analyse / vermoedelijke oorzaak
`apps/api/src/modules/quotes/quote-public.service.ts`:

```ts
async findByPublicToken(token: string) {
  const quote = assertFound(await this.prisma.quote.findUnique({
    where: { publicToken: token },      // ← geen orgId, geen tenantvergelijking
    …
```

Dezelfde ongebondenheid zit in `signQuote()`, `downloadPublicPdf()`, `addClientQuestion()` en
`downloadPublicAttachment()`. De controller (`PublicQuotesController`, `quotes.controller.ts:329`) injecteert geen
`@CurrentTenant()` en geeft die dus ook niet door.

Waarom **S2 en niet S1**: de token is een lang, ongeraadbaar geheim en fungeert zelf als capability — er is geen pad
waarbij org B *zonder* de token bij org A-data komt. Het is dus geen klassiek cross-tenant leesgat. Wat wél stuk is:
(a) de tenantgrens wordt op deze routes helemaal niet gehandhaafd, (b) een concurrent kan andermans offerte onder
zijn **eigen** merknaam/domein serveren (phishing/whitelabel-verwarring, de klant ziet `concurrent.inspexi.nl` in de
adresbalk terwijl het jouw offerte is), en (c) de abonnementsgate hangt aan de verkeerde organisatie.

## Advies
1. Injecteer `@CurrentTenant()` in `PublicQuotesController` en geef `tenant.orgId` door aan alle vijf de
   publieke servicemethodes; filter daarmee: `findFirst({ where: { publicToken: token, orgId } })`. Een token op het
   verkeerde subdomein levert dan een gewone 404 op — hetzelfde antwoord als een onbestaand token, dus geen oracle.
   Voor het superuser-domein (`mijn.*`, `orgId = null`) bewust kiezen: of ook weigeren, of expliciet doorlaten.
2. Verplaats `@RequiresFeature('CRM_COMPLEET')` van de controller naar de service, geëvalueerd tegen
   `quote.orgId` (de eigenaar) in plaats van tegen de bezoekende tenant.
3. Voeg een e2e-test toe in `cross-tenant.e2e-spec.ts`: geldige `publicToken` van org A op het subdomein van org B
   → 404 voor `GET`, `GET :token/pdf` en `POST :token/sign`.
