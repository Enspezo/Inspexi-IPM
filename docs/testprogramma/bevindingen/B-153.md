# B-153 — `POST /auth/refresh` zonder cookie geeft HTTP 200 met `success:false` i.p.v. 401

- **Testgeval:** SEC-14
- **Actor / rol:** Niet-geauthenticeerde client (portal / client-portal / PWA)
- **App:** API (:3001) · org: inspexidemo
- **Severity:** S3 (matig — verkeerde statuscode op het auth-herstelpad, geen datalek)
- **Type:** statuscode / foutafhandeling
- **Datum/tijd:** 2026-07-27 08:50

## Verwacht
Een refresh-poging zonder `refresh_token`-cookie is een niet-geauthenticeerd verzoek en hoort **401** te geven, net
als de andere faalpaden van hetzelfde endpoint (ongeldig token, verlopen token, verkeerde org geven alle drie wél
401 met een `statusCode`-veld). De eigen Swagger-annotatie van de route documenteert ook alleen 200 en **401**.

## Werkelijk
Ontbrekende cookie → **HTTP 200** met body `{"success":false,"message":"Geen refresh token"}`. De body mist
bovendien het `statusCode`-veld dat elk ander foutantwoord in deze API wel heeft.

## Reproductie

```bash
# 1) mét cookie (referentie) — 200 + nieuw accessToken
curl -s -c /tmp/cj.txt -X POST -H 'Host: inspexidemo.localhost' -H 'Content-Type: application/json' \
  -d '{"email":"manager@inspexi-demo.nl","password":"Password123!"}' \
  http://localhost:3001/api/v1/auth/login > /dev/null
curl -s -b /tmp/cj.txt -X POST -H 'Host: inspexidemo.localhost' \
  -w '\nHTTP %{http_code}\n' http://localhost:3001/api/v1/auth/refresh

# 2) ZONDER cookie
curl -s -X POST -H 'Host: inspexidemo.localhost' \
  -w '\nHTTP %{http_code}\n' http://localhost:3001/api/v1/auth/refresh

# 3) mét een onzin-cookie (ter vergelijking)
curl -s -X POST -H 'Host: inspexidemo.localhost' \
  -H 'Cookie: refresh_token=00000000-0000-4000-8000-000000000000' \
  -w '\nHTTP %{http_code}\n' http://localhost:3001/api/v1/auth/refresh
```

```
# 2) ZONDER cookie   ← afwijking

# 4) refresh-cookie van org A op testbedrijf.localhost

{"success":false,"message":"Uw account hoort niet bij deze organisatie","statusCode":401}

# 5) rotatie werkt: het zojuist gebruikte (oude) refresh-token
HTTP 401
{"success":false,"message":"Ongeldige of verlopen refresh token","statusCode":401}
```

## Analyse / vermoedelijke oorzaak
`apps/api/src/modules/auth/auth.controller.ts` r. 93–96:

```ts
const refreshToken = req.cookies?.['refresh_token'];
if (!refreshToken) {
  return { success: false, message: 'Geen refresh token' };   // ← return i.p.v. throw
}
```

Er wordt een gewone waarde geretourneerd in plaats van een `UnauthorizedException` gegooid, dus Nest gebruikt de
succes-statuscode van de route. Alle andere faalpaden lopen via `AuthService.refresh()` en gooien daar wél
`UnauthorizedException`.

**Impact:** clients die op de HTTP-status sturen (de gebruikelijke `if (!res.ok) → redirect /login`-constructie in
een fetch-interceptor) zien een 200 en concluderen dat de sessie hersteld is. Zij moeten nu extra op
`body.success === false` controleren. In `apps/portal/src/lib/api-client.ts` wordt de response wél op `success`
gecontroleerd, dus de portal komt er nu mee weg — maar het is een valstrik voor elke nieuwe client (PWA,
client-portal, integraties) en het is inconsistent met de gedocumenteerde 401.

## Advies
Vervang de `return` door `throw new UnauthorizedException('Geen refresh token');`. Dat maakt alle vier de
faalpaden van `/auth/refresh` uniform 401 met `statusCode` in de body. Controleer daarna of de portal- en
client-portal-interceptors bij een 401 op `/auth/refresh` netjes naar `/login` gaan (dat is het bestaande gedrag
voor de andere 401-varianten, dus naar verwachting geen aanpassing nodig).

## Status

**Opgelost in WP-C5** (branch `fix/wp-c5-config-validation`): `return { success:false }` →
`throw new UnauthorizedException('Geen refresh token')`. Alle faalpaden van `/auth/refresh`
zijn nu uniform 401 mét `statusCode`.

Interceptor-checks (clients):
- **Portal** (`apps/portal/src/lib/api-client.ts`): `refreshAccessToken()` checkt `!response.ok`
  → false → bestaand redirect-naar-login-pad. Geen aanpassing nodig.
- **PWA** (read-only gecontroleerd in `/Users/mathijs/VIBE/Inspexi-App-herstel`,
  `apps/inspectie-app/src/services/api/apiClient.ts` r. 74-123): de interceptor behandelt
  `!response.ok || !data?.success || !accessToken` als "cannot refresh" → `clearSession()` en
  géén retry (single-flight via `refreshPromise`). **Geen refresh-lus mogelijk**; de
  code-comment aldaar over "200 met success:false" is na deze fix alleen nog historisch.
- Test: e2e in `auth.e2e-spec.ts` (zonder cookie → 401 + statusCode + NL-melding).
