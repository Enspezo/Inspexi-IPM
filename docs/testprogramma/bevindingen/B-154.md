# B-154 — HTTP 500 op klantgerichte download-endpoints wanneer het opgeslagen bestand ontbreekt

- **Testgeval:** SEC-18
- **Actor / rol:** Anonieme hersteller (RepairSession-token, geen account)
- **App:** API (:3001) · org: inspexidemo · client-portal-flow `/herstel`
- **Severity:** S3 (matig — onafgevangen storage-fout, generieke Engelse 500 op een publieke route)
- **Type:** foutafhandeling / robuustheid
- **Datum/tijd:** 2026-07-27 08:52

## Verwacht
`GET /client/repair/declaration/pdf` op een afgeronde herstelsessie geeft 200 met de PDF, óf — als het bestand niet
(meer) beschikbaar is — een afgevangen fout met een Nederlandse melding (404 "De herstelverklaring is niet
beschikbaar" of 503). Het orakel van dit testprogramma is expliciet: **een 500 is altijd fout**.

## Werkelijk
Wanneer de `GeneratedDocument`-rij wél een `pdfUrl` heeft maar het object niet in de storage staat, slaat de
`ENOENT` van de storage-provider door naar de global exception filter:

```
HTTP 500
{"success":false,"message":"Internal server error","requestId":"927daa21-…","statusCode":500}
```

Hetzelfde geldt voor `GET /client/repair/photos/:id`. Beide routes zijn bereikbaar voor een **anonieme** bezoeker
met alleen een sessietoken.

## Reproductie

```bash
# afgeronde demo-sessie waarvan het PDF-object niet in deze UPLOAD_DIR staat
curl -s -i -H 'Host: inspexidemo.localhost' -H 'Authorization: Bearer demo-herstel-sessie' \
  http://localhost:3001/api/v1/client/repair/declaration/pdf | head -3

# zelfde sessie, foto uit de herstelmelding
curl -s -w '\nHTTP %{http_code}\n' -H 'Host: inspexidemo.localhost' -H 'Authorization: Bearer demo-herstel-sessie' \
  http://localhost:3001/api/v1/client/repair/photos/dbc5f06c-a554-4733-a817-86adffa766d7

# controle: een sessie waarvan het bestand er WEL is → 200 + echte PDF
curl -s -o /tmp/d.pdf -w 'HTTP %{http_code} type=%{content_type} bytes=%{size_download}\n' \
  -H 'Host: inspexidemo.localhost' -H 'Authorization: Bearer tp-herstel-afgerond' \
  http://localhost:3001/api/v1/client/repair/declaration/pdf
head -c 8 /tmp/d.pdf   # → %PDF-1.4
```

Overige SEC-18-controles op dezelfde sessie gedragen zich wél correct:

```
GET  /client/repair/session                     → 200 (COMPLETED blijft leesbaar, ondanks expiresAt 2026-07-11)
POST /client/repair/findings/:id/resolve        → 400 "Deze herstelsessie is al afgerond"
GET  /client/repair/session  (host inspexicompleet) → 401 "Ongeldige herstelsessie"
```

## Analyse / vermoedelijke oorzaak
`apps/api/src/modules/client-repair/client-repair.service.ts` r. 981–994 controleert wél of de rij en de `pdfUrl`
bestaan, maar niet of het object leesbaar is:

```ts
if (!document?.pdfUrl) {
  throw new NotFoundException('De herstelverklaring is nog niet ondertekend');
}
const buffer = await this.storage.download(document.pdfUrl);   // ← ENOENT slaat door
```

`LocalStorageProvider.download()` (`common/services/storage/local-storage.provider.ts`) doet een kale
`fs.readFile(fullPath)` zonder try/catch; er is wél een `exists()`-methode maar die wordt hier niet gebruikt.
Elke aanroeper van `storage.download()` heeft dus dezelfde blootstelling.

**Trigger in deze testomgeving (belangrijk voor reproduceerbaarheid):** de database staat op de gedeelde Postgres
:5433, maar `UPLOAD_DIR` is per checkout `./uploads`. De demo-seed (`SEED_DEMO=1`) is in een *andere* worktree
gedraaid; het bestand staat daardoor op
`…/.claude/worktrees/imp-prd-10-phase-4-5dd180/apps/api/uploads/f765ff41-…/documents/38725b6b-….pdf`
terwijl de API onder test uit `InspeXi-Beheer-test` draait. De seed zelf is dus niet stuk — maar dit is precies het
scenario dat in productie ook kan optreden (object-storage tijdelijk onbereikbaar, gefaalde/afgebroken upload,
migratie tussen buckets), en het faalgedrag hoort dan een nette fout te zijn in plaats van een 500.

## Advies
1. Vang de storage-fout af op de aanroepplaats:
   ```ts
   const buffer = await this.storage.download(document.pdfUrl).catch(() => {
     throw new NotFoundException('De herstelverklaring is niet beschikbaar');
   });
   ```
   en idem in `getResolutionPhoto()`/`photos/:id`.
2. Structureler: laat `StorageProvider.download()` een getypeerde `StorageObjectNotFoundError` gooien bij ENOENT en
   map die centraal in de exception filter naar 404 met een Nederlandse melding. Dan zijn álle download-routes
   (documenten, offerte-PDF's, gegenereerde rapporten, avatars) in één keer gedekt.
3. Los daarvan: overweeg voor de testomgeving een gedeelde `UPLOAD_DIR` (of een absolute pad-env) zodat een seed uit
   de ene worktree geen dangling `pdfUrl`-verwijzingen achterlaat voor een API uit een andere worktree.

## Status

**Opgelost in WP-C5** (branch `fix/wp-c5-config-validation`), conform advies 2 (structureel):
- Nieuwe getypeerde **`StorageObjectNotFoundError`** in
  `common/services/storage/storage.interface.ts` (met de storage-key als veld).
- `LocalStorageProvider.download()` vertaalt ENOENT ernaartoe; `R2StorageProvider.download()`
  doet hetzelfde voor NoSuchKey/404 — de mapping is provideronafhankelijk.
- De **global exception filter** mapt de fout centraal naar **404** met NL-melding
  "Het opgevraagde bestand is niet (meer) beschikbaar" en logt een **warn** mét storage-key
  (key komt nooit in de response). Dekt daarmee álle 35 download-call-sites (documenten,
  offerte-PDF's, rapporten, herstelverklaring/-foto's, avatars, logo's) in één keer.
  De filtertak is bewust minimaal en zelfstandig gehouden i.v.m. parallel filterwerk in WP-C1.
- Advies 3 (gedeelde UPLOAD_DIR voor de testomgeving) is een omgevingskeuze en geen codefix —
  open gelaten voor de orkestrator.
- Tests: 2 unit provider (ENOENT → typed error; EISDIR niet gemaskeerd) + 1 unit filter
  (404 NL zonder key-lek).
