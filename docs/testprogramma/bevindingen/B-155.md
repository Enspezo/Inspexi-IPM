# B-155 — Engelse foutmeldingen op auth-/validatiefouten in een verder Nederlandstalige API

- **Testgeval:** SEC-14, SEC-15, SEC-17 (waargenomen tijdens SEC-10 t/m SEC-18)
- **Actor / rol:** alle actoren (staf, client-realm, PWA)
- **App:** API (:3001) · alle orgs
- **Severity:** S4 (cosmetisch — geen functioneel effect, wel zichtbaar voor eindgebruikers)
- **Type:** taal / consistentie
- **Datum/tijd:** 2026-07-27 08:55

## Verwacht
`00-master-testplan.md` §3 (orakel) en `CLAUDE.md` ("UI labels, validatiemeldingen: **Nederlands**") schrijven
Nederlandse, begrijpelijke foutmeldingen voor. De API doet dat overal netjes — "Inspectieplan niet gevonden",
"Account is gedeactiveerd", "Uw sessie is verlopen — log opnieuw in met rapportnummer en postcode", "Deze functie
zit niet in uw abonnement". Op drie plekken lekt echter de Engelse framework-default door.

## Werkelijk
Drie categorieën Engelse meldingen die tot in de UI kunnen komen:

| Situatie | Melding | Herkomst |
|---|---|---|
| Ongeldig/ontbrekend/verlopen JWT | `"Unauthorized"` | Nest `AuthGuard('jwt')` default |
| Token van een gedeactiveerde of verwijderde gebruiker | `"User not found or inactive"` | eigen code, maar Engels |
| Ongeldige UUID in een route-parameter | `"Validation failed (uuid is expected)"` | `ParseUUIDPipe` default |

## Reproductie

```bash
MT=<geldig staf-accessToken>

# 1) geknoeid token
curl -s -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer ${MT%?}X" \
  http://localhost:3001/api/v1/auth/me

# 2) token van een user die zojuist gedeactiveerd is
curl -s -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $BO_TOKEN" \
  http://localhost:3001/api/v1/auth/me

# 3) ongeldige UUID in de route
CT=<clienttoken>
curl -s -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $CT" \
  http://localhost:3001/api/v1/client/inspections/not-a-uuid
```

## Bewijs

```
# 1) geknoeid token  (idem: onzin-token, leeg Bearer, zelf-gemint verlopen token,
#     clienttoken op staf-realm, staftoken op client-realm)
HTTP 401
{"success":false,"message":"Unauthorized","statusCode":401}

# 2) gedeactiveerde user met nog geldig token
HTTP 401
{"success":false,"message":"User not found or inactive","statusCode":401}

# 3) ongeldige UUID
HTTP 400
{"success":false,"message":"Validation failed (uuid is expected)","statusCode":400}
```

Ter contrast, dezelfde flow ná uitloggen/opnieuw inloggen geeft wél Nederlands:

```
POST /auth/login met gedeactiveerd account → 401 {"message":"Account is gedeactiveerd"}
POST /auth/refresh, verkeerde org          → 401 {"message":"Uw account hoort niet bij deze organisatie"}
GET  /auth/me met reset-token als Bearer   → 401 {"message":"Ongeldig token-type"}
```

## Analyse / vermoedelijke oorzaak
- `"Unauthorized"` is de default van Nest's `AuthGuard`; `JwtAuthGuard` overschrijft `handleRequest()` niet voor het
  generieke faalgeval (wel voor het token-type, zie de Nederlandse "Ongeldig token-type").
- `"User not found or inactive"` staat als letterlijke Engelse string in de JWT-strategy/validatie.
- `"Validation failed (uuid is expected)"` is de default `exceptionFactory` van `ParseUUIDPipe`.

Geen functioneel effect en geen informatielek — puur taalconsistentie. Wel zichtbaar: de portal toont de
`message` uit de API-response in toasts en foutboxen.

## Advies
1. Overschrijf `handleRequest()` in `JwtAuthGuard` zodat het generieke faalgeval
   `new UnauthorizedException('Niet ingelogd of sessie verlopen')` gooit.
2. Vervang de string `'User not found or inactive'` door bijv. `'Account bestaat niet meer of is gedeactiveerd'`.
3. Geef `ParseUUIDPipe` een `exceptionFactory` (of registreer er één globaal) die
   `'Ongeldige identificatie'` teruggeeft — bij voorkeur via een kleine gedeelde `ParseUuid()`-helper in `@/common`
   zodat alle controllers hem in één keer gebruiken.
