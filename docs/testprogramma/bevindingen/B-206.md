# B-206 — Constateringen uit de PWA synchroniseren nooit: `visualInspectionId` krijgt de checklistItemId toegewezen (stil dataverlies)

- **Testgeval:** INS-16 (raakt ook INS-15, INS-18, INS-19)
- **Actor / rol:** Inspecteur / INSPECTEUR (`inspecteur@inspexi-demo.nl`)
- **App:** Inspexi-App PWA (:5176) → Beheer-API (:3001) · org: inspexidemo
- **Severity:** S1 (blokkerend — dataverlies bij sync)
- **Type:** foutieve FK-toewijzing / sync-contract
- **Datum/tijd:** 2026-07-27 10:08

## Verwacht
Een constatering die de inspecteur in het veld vastlegt, wordt bij de eerstvolgende sync naar de server
gepusht en is daarna zichtbaar in de portal. Mislukt dat, dan moet de inspecteur dat **zien**.

## Werkelijk
Elke constatering die via de checklist (NOK → CreateFindingSheet) wordt aangemaakt, krijgt
`visualInspectionId = checklistItemId`. Die id bestaat niet in `imp_visual_inspections`, dus de server
weigert het record met een foreign-key-fout. Het resultaat:

- de constatering komt **nooit** op de server (`SELECT count(*) … WHERE short_description LIKE 'INS16%'` → `0`);
- het lokale record blijft eeuwig `_pendingSync: true` en wordt eindeloos opnieuw geprobeerd
  (`syncRetryMeta.attempts` loopt op, `deadLetter: false`);
- de UI toont **geen** foutmelding — alleen het amberkleurige pending-pilletje "1" (zie B-211).

De inspecteur denkt dat zijn werk verstuurd is. Bij het wissen/opnieuw installeren van de app of het
wisselen van toestel is de constatering definitief verloren.

## Reproductie
1. Login als `inspecteur@inspexi-demo.nl` op `inspexidemo.localhost:5176`, wacht de initiële sync af.
2. *(Harness, zie B-204: de PWA haalt checklists nooit op — vul `cachedChecklists` met `/checklists/:id`.)*
3. Open `/inspections/cc495211-…/assets/1fde2f90-…/visual`.
4. Klik **NOK** op item 1 → sheet "Constatering toevoegen" → **Eigen constatering**.
5. Vul beschrijving + aanbeveling, kies classificatie **Kritiek**, klik **Opslaan**.
6. Klik het sync-pilletje rechtsboven; wacht ~8 s.
7. `PGPASSWORD=… psql -h localhost -p 5433 -U inspectie -d inspectie -c "SELECT count(*) FROM imp_findings WHERE short_description LIKE 'INS16%'"` → **0**.

## Analyse / vermoedelijke oorzaak
`apps/inspectie-app/src/features/visual-inspection/CreateFindingSheet.tsx:172`:

```ts
visualInspectionId: checklistItemId,
```

De prop `checklistItemId` (het aangeklikte checklist-item) wordt rechtstreeks in het veld
`visualInspectionId` geschreven. Dat er lokaal geen FK-controle is, maskeert de fout tot aan de push.
De onderliggende oorzaak is dat de PWA überhaupt geen `VisualInspection`-record aanmaakt wanneer een
checklist wordt ingevuld (zie B-210: de checklistantwoorden worden nergens opgeslagen), dus er ís geen
geldige `visualInspectionId` om naar te verwijzen.

## Advies
1. Zet `visualInspectionId` op `null` zolang er geen echte `VisualInspection` bestaat, en schrijf de
   checklist-koppeling in het daarvoor bedoelde veld `checklistItemId`.
2. Los B-210 op: maak bij het invullen/afronden van een checklist een `VisualInspection`-record aan en
   push dat vóór de bijbehorende findings (volgorde-afhankelijkheid in `push.ts`).
3. Voeg een client-side integriteitscheck toe vóór de push: verwijst een FK naar een record dat lokaal
   niet bestaat en niet mee gepusht wordt → niet versturen, maar de gebruiker waarschuwen.
4. Laat een record na N mislukte pogingen naar een zichtbare "dead letter"-status gaan met een
   expliciete melding in de UI (nu blijft het stil retryen).

## Status
**Opgelost** (WP-A2 — PWA-PR `fix/wp-a2-data-loss-stop` + Beheer-PR `fix/wp-a2-sync-contract-tests`).
Root cause bevestigd zoals beschreven (`CreateFindingSheet.tsx:172` schreef het checklist-item-id in
`visualInspectionId`; `checklistItemId` bleef `undefined`).

- **PWA:** `CreateFindingSheet` krijgt de échte `visualInspectionId` als prop (de `VisualInspection`
  wordt bij NOK eerst idempotent aangemaakt/gepersisteerd — zie B-210) en schrijft het checklist-item
  in het eigen veld `checklistItemId` (alleen als het een echte UUID is; statische fallback-items als
  `nen1010-hv-001` blijven eruit, de server-kolom is `@db.Uuid`). Advies 3 is geïmplementeerd als
  FK-integriteitscheck in `push.ts`: een record met een lokaal onbekende FK wordt niet verstuurd maar
  als `failed` gemarkeerd met een NL-melding (zichtbaar via de WP-A1-`SyncErrorBadge`); een record dat
  wacht op een nog-niet-gesyncte ouder wordt stil uitgesteld. **Dexie v15-repair** verplaatst op
  bestaande toestellen een foute `visualInspectionId` (pending records) naar `checklistItemId`.
- **Beheer:** de push verwerkt `visualInspections`/`measurementRecords` nu vóór `findings`
  (ouder-vóór-kind in `SYNC_ENTITIES`), en `findings.fkChecks` is uitgebreid met `visualInspectionId`
  + `measurementRecordId` → nette NL-400 ("Visuele inspectie niet gevonden") i.p.v. een rauwe
  Prisma-P2003, en geen cross-tenant koppeling meer mogelijk. Regressiedekking in
  `apps/api/test/sync-contract.e2e-spec.ts` (keten-push VI+finding in één batch; oude bugvorm → NL-400).
- Advies 4 (dead-letter) was al gerealiseerd in WP-A1.
