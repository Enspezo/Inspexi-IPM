# B-209 — Serverwijzigingen worden stil overschreven zolang `synced_at` NULL is: geen conflictdetectie op 49 van 52 assetnodes

- **Testgeval:** INS-39
- **Actor / rol:** Inspecteur / INSPECTEUR (PWA) versus MANAGER (portal)
- **App:** Inspexi-App PWA (:5176) ↔ Beheer-API (:3001) · org: inspexidemo
- **Severity:** S2 (ernstig — back-officecorrecties verdwijnen zonder spoor of melding; grenst aan S1)
- **Type:** onvolledige optimistic-locking
- **Datum/tijd:** 2026-07-27 09:57

## Verwacht
Wijzigt de portal een record ná de laatste pull van de PWA, en pusht de PWA daarna zijn eigen versie, dan
detecteert de server een conflict en toont de PWA de ConflictBanner met een keuze
"Mijn versie" / "Serverversie" (zoals wél gebeurt in het geslaagde deel van INS-39).

## Werkelijk
De conflictdetectie werkt uitsluitend voor records die al eens **door een device** gepusht zijn. Voor alle
overige records (geseed, of aangemaakt/gewijzigd in de portal) is `synced_at` NULL; de PWA houdt dan lokaal
`syncedAt: undefined` aan en de server slaat zijn optimistic-check volledig over. De push overschrijft dan
zonder conflict, zonder waarschuwing en zonder audit-signaal wat de portal net had gecorrigeerd.

In deze database geldt dat voor **49 van de 52** assetnodes.

Bewezen scenario: de servernaam "TP Onderverdeler B1 SERVERVERSIE" werd door een PWA-push teruggezet naar
de oude clientwaarde "TP Onderverdeler B1 🔧🚀", zonder conflictrij en zonder banner.

## Reproductie
1. Login als `inspecteur@inspexi-demo.nl` en wacht de sync af (asset `9b2ef548-…` heeft `synced_at IS NULL`).
2. Open het asset-detail, ga offline en klik "Start inspectie" (lokale wijziging).
3. Wijzig ondertussen hetzelfde record aan serverzijde:
   ```sql
   UPDATE imp_asset_nodes SET name='TP Onderverdeler B1 SERVERVERSIE', updated_at=now()
   WHERE id='9b2ef548-9c8f-4284-b0be-534dff073906';
   ```
4. Ga online en synchroniseer.
5. Resultaat: **geen** ConflictBanner, `imp_sync_queue` leeg, en:
   ```sql
   SELECT name FROM imp_asset_nodes WHERE id='9b2ef548-…';
   -- TP Onderverdeler B1 🔧🚀      <-- serverwijziging weg
   ```
6. Contraproef met asset `89d99fef-…` (heeft wél `synced_at`): identieke stappen → ConflictBanner
   verschijnt, `imp_sync_queue` krijgt een `conflict`-rij, resolve werkt.

## Analyse / vermoedelijke oorzaak
`apps/api/src/modules/sync/sync.service.ts` → `applyUpdate()`:

```ts
const clientSynced = data.syncedAt ? new Date(data.syncedAt) : null;
if (clientSynced && existing.updatedAt > clientSynced) { /* conflict */ }
```

Wanneer `data.syncedAt` ontbreekt (`null`/`undefined`) valt de hele conflicttak weg en volgt een
onvoorwaardelijke update — "geen basis bekend" wordt behandeld als "geen conflict", terwijl het juist
**onbekend** is. `synced_at` wordt server-side kennelijk alleen gevuld bij een device-push, dus geseede
en via de portal aangemaakte records missen die waarde permanent.

Aanvullend: ook `InspectionPlan` bleek lokaal `syncedAt: null` te hebben na het offline indienen — voor
plannen is de conflictdetectie dus eveneens uitgeschakeld (in de test bleef `projectName` toevallig gespaard
omdat de PWA dat veld niet meestuurde, maar de bescherming ontbreekt).

## Advies
1. Fail closed: ontbreekt `syncedAt` op een **update**, behandel dat als conflict, óf val terug op een
   vergelijking met `updatedAt` uit de payload.
2. Vul `synced_at` bij elke serverzijdige schrijfactie (REST én seed), zodat elk record een pull-basis heeft.
   Alternatief: gebruik `updatedAt` als versie-anker en laat de client die waarde teruggeven.
3. Laat de PWA de laatst gepullde `updatedAt`/`syncedAt` per record vasthouden en altijd meesturen —
   inclusief `inspectionPlans`.
4. Voeg een e2e-test toe: portal wijzigt record X ná de pull, PWA pusht X → verwacht een conflictrij,
   niet een overschrijving.
