# B-212 — Rauwe Prisma-fout met serverpad, broncoderegels en volledige payload wordt aan de client teruggegeven

- **Testgeval:** INS-16, INS-26 (waargenomen in elke mislukte `/sync/push`)
- **Actor / rol:** Inspecteur / INSPECTEUR (elke geauthenticeerde client)
- **App:** Beheer-API (:3001), endpoint `POST /api/v1/sync/push` · org: inspexidemo
- **Severity:** S3 (matig — informatielek/attack surface, geen directe schade)
- **Type:** ontbrekende foutafhandeling / information disclosure
- **Datum/tijd:** 2026-07-27 09:31

## Verwacht
Een mislukte record-write levert een korte, functionele foutmelding op (NL), zonder implementatiedetails.
Interne fouten horen server-side gelogd te worden, niet naar de client te reizen.

## Werkelijk
De volledige Prisma-uitzondering wordt letterlijk in `errors[].error` gezet. Die bevat:

- het **absolute bestandspad op de server**: `/Users/mathijs/VIBE/InspeXi-Beheer-test/apps/api/src/modules/sync/sync.service.ts:546:19`
- **broncoderegels** rond het faalpunt (`543 return { ...ref, status: 'success' }` …)
- de **volledige create-payload**, inclusief `orgId`, `createdBy`, de templatesnapshot en alle veldwaarden
- de exacte **databaseconstraint-naam**: `imp_findings_visual_inspection_id_fkey (index)`

De melding is bovendien Engels en onbegrijpelijk voor een eindgebruiker.

## Reproductie
1. Login als inspecteur; volg de reproductie van B-206 of B-207.
2. Lees de respons van `POST /api/v1/sync/push` (201) → veld `data.errors[0].error`.

## Bewijs
```json
{"entityType":"finding","entityId":"cfdbabb9-…","status":"failed",
 "error":"\nInvalid `model.create()` invocation in\n/Users/mathijs/VIBE/InspeXi-Beheer-test/apps/api/src/modules/sync/sync.service.ts:546:19\n\n  543   return { ...ref, status: 'success' };\n  544 }\n  545 \n→ 546 await model.create(\nForeign key constraint violated: `imp_findings_visual_inspection_id_fkey (index)`"}
```
En bij het meetstaat-record de complete `data: { … }`-payload met `orgId` en `createdBy` (zie B-207).

Dezelfde tekst wordt door de PWA opgeslagen in `syncRetryMeta.lastError` en blijft dus ook in IndexedDB
op het toestel achter.

## Analyse / vermoedelijke oorzaak
In `sync.service.ts` wordt de per-record fout opgevangen en ongefilterd doorgegeven:
`catch (e) { errors.push({ …, error: e.message }) }`. Prisma's `message` bevat in development standaard de
volledige "Invalid invocation"-context. In productie (`errorFormat`) is dat vaak korter, maar het pad en de
constraintnaam blijven meestal zichtbaar.

## Advies
1. Map bekende Prisma-foutcodes op functionele NL-meldingen (P2003 → "Verwijzing naar een niet-bestaand
   record", P2002 → "Deze waarde bestaat al") en stuur alleen die naar de client.
2. Log de volledige uitzondering server-side met een correlatie-id en geef dat id mee in de respons.
3. Zet `errorFormat: 'minimal'` op de PrismaClient in niet-lokale omgevingen.
4. Sla in de PWA alleen de gemapte melding op in `syncRetryMeta.lastError`.
