# B-217 — INSPECTEUR kan via `/sync/push` de `reviewerId` van een inspectieplan zetten (ook zichzelf)

- **Testgeval:** INS-41
- **Actor / rol:** Inspecteur / INSPECTEUR (`inspecteur@inspexi-demo.nl`)
- **App:** Beheer-API (:3001) · org: inspexidemo
- **Severity:** S3 (matig — vier-ogen-rol wordt door de uitvoerder zelf gestuurd; de harde gate blijft dicht)
- **Type:** te ruime schrijf-whitelist
- **Datum/tijd:** 2026-07-27 10:02

## Verwacht
De beoordelaar van een plan is een management-beslissing. Een INSPECTEUR hoort `reviewerId` niet te kunnen
zetten — zeker niet op zichzelf, want dat ondermijnt het vier-ogen-principe.

## Werkelijk
`reviewerId` staat in de sync-whitelist voor `inspectionPlans`. Een push met een `reviewerId` wordt
geaccepteerd zolang de gebruiker in dezelfde organisatie zit (`userFkChecks` controleert alleen
cross-tenant). De inspecteur zette zichzelf als beoordelaar van plan TP-RAP-004.

De harde gate blijft wél overeind: `reviewedAt` is niet client-schrijfbaar, dus `statusCode → completed`
wordt nog steeds geweigerd (zie de PASS bij INS-41). Het risico is dus routing/verantwoordelijkheid,
niet een directe omzeiling.

## Reproductie
```bash
curl -s -X POST -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $INSPECTEUR_TOKEN" \
 -H 'Content-Type: application/json' \
 -d '{"deviceId":"ins41-device","changes":{"inspectionPlans":[{"operation":"update","data":{
      "id":"c4ad6696-8878-4247-b305-f2e376c9335e",
      "reviewedAt":"2026-07-27T00:00:00.000Z",
      "reviewerId":"8bebe845-68cb-4d33-ad48-e7aa22561055"}}]}}' \
 http://localhost:3001/api/v1/sync/push
```

## Bewijs
- Respons: `201`, `processed.inspectionPlans: 1`, `errors: []`
- DB daarna:
  ```
  reference_number | status         | reviewed_at | reviewer_id
  TP-RAP-004       | pending_review |             | 8bebe845-68cb-4d33-ad48-e7aa22561055   <-- de inspecteur zelf
  ```
  `reviewed_at` bleef leeg → dat veld is correct server-owned.
- Vervolgpush met `statusCode: "completed"` → geweigerd met
  "Dit plan moet eerst beoordeeld worden (vier-ogen-principe)". Gate werkt.

*(reviewer_id is na de test teruggezet op NULL.)*

## Analyse / vermoedelijke oorzaak
`apps/api/src/modules/sync/sync-mapper.ts`, entiteit `inspectionPlans`:

```ts
allowed: [ …, 'assignedTo', 'reviewerId', 'installationResponsibleId', 'statusCode', … ],
userFkChecks: ['assignedTo', 'reviewerId'],   // alleen cross-tenant-check
```

De `userFkChecks` valideren dat de gebruiker bestaat en tot dezelfde org behoort, maar niet of de
*pushende* gebruiker deze toewijzing mag doen, en niet of de doelgebruiker een review-rol heeft.

## Advies
1. Haal `reviewerId` (en waarschijnlijk `assignedTo`) uit de sync-whitelist — dat zijn planningsvelden die
   via de portal horen te lopen.
2. Kan dat niet: sta ze alleen toe wanneer de pushende gebruiker een management-/werkvoorbereidersrol heeft,
   en weiger een `reviewerId` die gelijk is aan `assignedTo` of aan de pushende gebruiker.
3. Valideer dat de doelgebruiker in `REVIEW_ROLES` zit.
4. Log de wijziging in `PlanningHistory`/audit — nu is de herkomst van zo'n toewijzing niet herleidbaar.

## Status
**Opgelost in WP-C3** (branch `fix/wp-c3-sync-hardening`) via **beslispunt A6-optie (b): rol-guard** — advies 1 (whitelist-versmalling) bleek niet mogelijk.
- **A6-check (waarom optie b):** de PWA (`Inspexi-App-herstel`, dev) pusht inspectieplannen als het **volledige lokale record** minus `orgId`/interne vlaggen (`services/sync/push.ts`: `const { orgId, _pendingSync, _deleted, ...rest } = plan`) — `assignedTo` en `reviewerId` reizen dus als echo in élke plan-push mee, en de offline `submitForReview` schrijft `reviewerId` bovendien actief in het lokale record. Velden uit de whitelist halen zou legitieme pushes stilzwijgend van betekenis veranderen; daarom rol-guard i.p.v. contractversmalling.
- **Guard** (`sync.service.assertPlanAssignmentRole`, push create/update/adopt + resolve): alleen een **wijziging** t.o.v. de serverstaat wordt geguard (echo's passeren — de PWA blijft gewoon werken). Pushers zonder REVIEW_ROLES (SUPERUSER/ORG_ADMIN/MANAGER/WERKVOORBEREIDER) krijgen bij een wijziging een per-record NL-fout: `Alleen management- of werkvoorbereidingsrollen mogen de toewijzing of beoordelaar van een inspectieplan wijzigen`. Uitzondering: een offline aangemaakt plan mag door de maker aan zichzelf toegewezen worden (`assignedTo === pusher` bij create). Conflict-bound updates doorlopen eerst het conflictpad; `resolve` draait de guard alsnog over de gekozen data.
- **Advies 2 (weiger `reviewerId === pusher`)** is bewust NIET geïmplementeerd — per werkpakket-instructie beslispunt-materie (A6); alleen de rol telt. **Advies 3 (doelgebruiker in REVIEW_ROLES)** idem: niet afgedwongen, zelfde beslispunt-ruimte; de REST-paden doen dit vandaag ook niet.
- **Advies 4 (herleidbaarheid):** `InspectionPlan` zit al in `AUDITED_MODELS` — een via sync gewijzigde `reviewerId`/`assignedTo` levert een UPDATE-audit-row met van→naar en de pushende gebruiker; geen extra logging nodig.
- Het repro-scenario (INSPECTEUR zet zichzelf als reviewer op TP-RAP-004) geeft nu een `errors[]`-record en géén write.
