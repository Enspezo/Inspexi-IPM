# B-222 — Constatering-classificatie is hardgecodeerd (`risico`): een "Kritiek"-constatering uit de PWA wordt nooit `isCritical`

- **Testgeval:** INS-19 (raakt PRD-14 online herstel / herinspectie)
- **Actor / rol:** Inspecteur / INSPECTEUR
- **App:** Inspexi-App PWA (:5176) ↔ Beheer-API (:3001) · org: inspexidemo
- **Severity:** S2 (ernstig — verkeerde businessuitkomst: kritieke bevindingen worden niet als kritiek herkend)
- **Type:** configuratie genegeerd / hardgecodeerd vocabulaire
- **Datum/tijd:** 2026-07-27 10:08

## Verwacht
De classificatiekeuze komt uit het geconfigureerde classificatiemodel van de organisatie. Kiest de
inspecteur de kritieke optie (in deze org `SEVERITY = C1`, "Gevaarlijk — direct herstellen"), dan zet de
server `Finding.isCritical = true`, wat de PRD-14-flow (online herstel + `HERINSPECTIE_VOORSTEL`) voedt.

## Werkelijk
Bij een "Eigen constatering" (geen finding-template, en de org heeft er 0) toont de sheet een **vaste**,
in de code opgenomen lijst Kritiek / Ernstig / Gering / Aandachtspunt / Positief, en schrijft de keuze weg
als:

```json
"classificationValues": { "risico": "kritiek" }
```

De organisatie kent echter geen kenmerk `risico`. De gecachte modellen zijn:

| model | kenmerk | opties |
|---|---|---|
| `NEN1010_DEFAULT` | `SEVERITY` | C1 (isCritical = **true**), C2, C3, FI |
| `SCOPE8_DEFAULT` | `CATEGORY` | A, B, C |

De server kan `{"risico":"kritiek"}` dus met geen mogelijkheid op `ClassificationOption.isCritical`
afbeelden; `computeFindingCriticalField()` vindt geen match en `isCritical` blijft `false`.

Bovendien bereikt het record de server sowieso nooit (B-206) — maar ook ná herstel van B-206 zou de
kritiekmarkering fout blijven.

## Reproductie
1. Login als `inspecteur@inspexi-demo.nl`; harness-cache voor checklists (B-204).
2. `/inspections/cc495211-…/assets/1fde2f90-…/visual` → **NOK** → **Eigen constatering**.
3. Kies **🔴 Kritiek**, vul beschrijving + aanbeveling, sla op.
4. Inspecteer het lokale record: `classificationValues = {"risico":"kritiek"}`.
5. Vergelijk met de configuratie:
   ```sql
   SELECT o.code, o.is_critical, c.code AS charcode
   FROM imp_classification_options o
   JOIN imp_classification_characteristics c ON c.id = o.characteristic_id;
   -- C1 | t | SEVERITY   <-- de enige kritieke optie
   -- C2 | f | SEVERITY   … A/B/C | f | CATEGORY
   ```

## Bewijs
- Lokaal record: `{"classificationValues":{"risico":"kritiek"}}`
- Gecachte modellen: `[{code:"NEN1010_DEFAULT",chars:[{code:"SEVERITY",opts:["C1","C2","C3","FI"]}]},
  {code:"SCOPE8_DEFAULT",chars:[{code:"CATEGORY",opts:["A","B","C"]}]}]`
- Screenshot: `bevindingen/img/INS16-constatering.png` (de vaste 5 knoppen)
- Bestaande findings uit de seed gebruiken wél de juiste vocabulaire ("Gevaarlijk — direct herstellen",
  "Onveilig — herstel aanbevolen") — de PWA-route wijkt dus af van de rest van het systeem.

## Analyse / vermoedelijke oorzaak
`src/features/visual-inspection/CreateFindingSheet.tsx`:

- regel 127 en 148: `setClassificationValues({ risico: "gering" })` als default;
- regel 287-301: een hardgecodeerde array `["kritiek", …]` met
  `onClick={() => setClassificationValues({ risico: cls })}`.

Deze tak is de fallback voor het geval er géén classificatiemodel aan de constatering hangt. De
model-gedreven tak (regels 243-257, met `char.code` / `opt.code`) is wél correct, maar wordt alleen bereikt
via een finding-template met `classificationModelId`. Omdat deze organisatie 0 finding-templates heeft
(`SELECT count(*) FROM imp_finding_templates` → 0) valt élke constatering in de hardgecodeerde tak.

## Advies
1. Laat de fallback het **standaard classificatiemodel van het normtype** van het plan gebruiken
   (`NEN1010_DEFAULT` bij een NEN1010-inspectie) in plaats van een vaste `risico`-lijst.
2. Is er echt geen model, blokkeer dan opslaan met een duidelijke melding in plaats van een fictief
   vocabulaire weg te schrijven — nu ontstaat er stille datavervuiling.
3. Valideer server-side in de `/sync/push` dat `classificationValues` alleen bestaande
   kenmerk-/optiecodes bevat (nu wordt elke JSON geaccepteerd).
4. Voeg een e2e-test toe: PWA-constatering met de kritieke optie → `Finding.isCritical = true` en de
   herinspectie-trigger armt.
