# B-301 — Relatienaam van 220 tekens blaast de kolombreedte op; alle overige kolommen verdwijnen uit beeld

- **Testgeval:** BO-03
- **Actor / rol:** Backoffice / MANAGER
- **App:** Portal (:5173) · org: inspexidemo
- **Severity:** S3 (matig — overzicht wordt onbruikbaar, geen dataschade)
- **Type:** grenswaarde / layout
- **Datum/tijd:** 2026-07-27 10:33

## Verwacht
Volgens het script: "Aangemaakt (geen backend-max); overzicht **kapt netjes af**, breekt layout niet."
De naamkolom zou moeten truncaten (`truncate` / `max-width`), zodat Type, E-mail, Telefoon, Stad,
Eigenaar, Klantgroep en Leverancier zichtbaar blijven.

## Werkelijk
De relatie `TP LLLL…` (220 tekens, geen spaties) wordt netjes opgeslagen, maar in `/contacts` rekt de
kolom `Naam` op tot **1812 px**. De tabel wordt daardoor **2905 px** breed in een container van
**1110 px**; er verschijnt een horizontale scrollbar en **alle overige kolommen staan buiten beeld**
voor *elke* rij, niet alleen voor de lange. Ook de aanvragenlijst (`/requests`, `TP-AV-008`,
2103-teken titel) vertoont hetzelfde gedrag.

Gemeten in de browser:
```js
{"tableW":2905,"containerW":1110,"scrollW":2905,
 "cells":[{"w":1812,"txt":"TP VIP Installaties BV"},{"w":127,"txt":"Bedrijf"}, …]}
```

## Reproductie
1. Login `manager@inspexi-demo.nl` op `http://inspexidemo.localhost:5173`.
2. Ga naar **Relaties → Overzicht**.
3. De rij `TP LLLLLL…` (220 tekens) staat in de lijst.
4. Alleen de kolom "Naam" is nog zichtbaar; scroll horizontaal om Type/E-mail/… te zien.

## Bewijs
- HTTP: `GET /api/v1/contacts?page=1&limit=20` → 200 (data zelf is correct)
- Backend accepteert ook 300 tekens: `POST /api/v1/contacts` met 300× `X` → **201**
- Console: geen fouten
- Screenshot: `bevindingen/img/B-301-lange-naam-tabel.png`

## Analyse / vermoedelijke oorzaak
De naamcel heeft geen `max-width` + `truncate`/`overflow-hidden`. Bij een string zonder spaties kan de
browser niet afbreken, dus groeit de kolom tot de volledige tekstbreedte. De Kanban-weergave van
aanvragen doet dit wél goed (daar wrapt de titel binnen de kaart), dus het probleem zit specifiek in de
tabelcomponent.

## Advies
- `max-w-[…] truncate` (of `overflow-hidden text-ellipsis whitespace-nowrap`) op de naam-/titelkolom,
  met de volledige waarde in een `title`-attribuut.
- Overweeg daarnaast een backend-`@MaxLength` op `companyName` / `Request.title` (nu ongelimiteerd).

## Status
**Opgelost** (WP-C4, branch `fix/wp-c4-docgen-overflow`, 2026-07-27).

- `apps/portal/src/components/ui/table.tsx`: elke `<td>` krijgt nu standaard **`max-w-xs truncate`**
  (i.p.v. alleen `whitespace-nowrap`), zodat één 220-teken waarde de kolom niet meer tot ~1800 px kan
  oprekken; de overige kolommen blijven in beeld. De **volledige waarde** staat in het
  `title`-attribuut (ook wanneer de cel een link/knop rendert — tekstinhoud wordt recursief
  geëxtraheerd; cellen zonder tekst, bv. icoon-knoppen, krijgen géén title).
- **Escape**: een kolom die zelf een `max-w-*`-klasse meegeeft via het bestaande
  `column.className` (bv. `max-w-none`) behoudt het oude nowrap-gedrag zonder truncatie.
- Fix zit in de gedeelde `Table`-component en geldt dus voor **alle** overzichten die 'm gebruiken
  (~46 pagina's), waaronder de gemelde `/contacts` (Naam) en `/requests` (Titel, 2103 tekens).
- Backend-`@MaxLength` op `companyName`/`Request.title` is hier bewust **niet** meegenomen
  (contractwijziging; ligt buiten WP-C4 — zie het advies hierboven als los beslispunt).
- Vitest-dekking: truncate-klassen + title bij lange waarde, geneste elementen, icoon-knop zonder
  title, `max-w-none`-escape, combinatie met `text-right`.
