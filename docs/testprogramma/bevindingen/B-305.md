# B-305 — Portal vraagt overal `limit=200` terwijl de API op 100 aftopt: 25+ dropdowns/lijsten blijven leeg (o.a. "Nieuwe inspectie" onbruikbaar)

- **Testgeval:** BO-41 (blokkerend), raakt ook BO-09-achtige modals
- **Actor / rol:** Backoffice / MANAGER
- **App:** Portal (:5173) + API (:3001) · org: inspexidemo
- **Severity:** S2 (ernstig — gouden pad "nieuw inspectieplan" breekt; systemisch over veel schermen)
- **Type:** contract-mismatch frontend/backend
- **Datum/tijd:** 2026-07-27 11:24

## Verwacht
De modal **Inspecties → Inspectie aanmaken** vult de dropdown "Opdrachtgever" met de relaties van de
org, zodat een backoffice-medewerker een inspectieplan kan aanmaken.

## Werkelijk
De dropdown bevat **alleen de placeholder** `— Kies opdrachtgever —`. Aanmaken is daardoor onmogelijk:
"Opdrachtgever is verplicht" blijft staan. Oorzaak: de modal doet
`GET /api/v1/contacts?limit=200`, en de gedeelde paginatie-DTO cap't op `@Max(100)`:

```
GET /api/v1/contacts?limit=200 → 400 {"success":false,"message":"limit must not be greater than 100"}
GET /api/v1/contacts?limit=100 → 200
```

De 400 wordt niet getoond; de query faalt stil en de lijst blijft leeg.

**Dit is systemisch.** Endpoints die op `limit=200` een 400 geven:

| Endpoint | `?limit=200` |
|---|---|
| `/contacts` | **400** |
| `/quotes` | **400** |
| `/tasks` | **400** |
| `/products` | **400** |
| `/work-orders` | **400** |
| `/quote-templates` | **400** |
| `/finding-templates` | **400** |
| `/inspection-plans` | **400** |
| `/requests`, `/projects`, `/planning`, `/measurement-instruments` | 200 (eigen DTO met `@Max(200)`) |

En de portal roept `limit=200` aan op minimaal 25 plaatsen, o.a.:

- `pages/inspections/components/create-inspection-modal.tsx:56` — `useContacts({ limit: 200 })`
- `pages/tasks/components/create-task-modal.tsx:78-80` — contacts, requests, quotes
- `pages/contacts/components/create-contact-person-modal.tsx:31` — contacts
- `components/documents/upload-document-modal.tsx:94-102` — contacts, requests, quotes, tasks, products, work-orders
- `pages/quotes/quotes-page.tsx:69` en `components/quote-template-switcher.tsx:25` — quote-templates
- `pages/measurement-sheet-templates/components/field-modal.tsx:124` — finding-templates
- `pages/inspections/components/create-asset-modal.tsx:39` — inspection-plans

## Reproductie
1. Login `manager@inspexi-demo.nl` op `http://inspexidemo.localhost:5173`.
2. **Inspecties** → `+` → **Inspectie aanmaken**.
3. Klap "Opdrachtgever" open: alleen `— Kies opdrachtgever —`.
4. DevTools/Network: `GET /api/v1/contacts?limit=200 → 400 Bad Request`.

## Bewijs
- HTTP: `GET /api/v1/contacts?limit=200` → **400** `limit must not be greater than 100`
- Screenshot: `bevindingen/img/B-305-lege-opdrachtgever-dropdown.png`
- Console: geen JS-fouten (de fout wordt door TanStack Query opgeslokt)

## Analyse / vermoedelijke oorzaak
Bekende valkuil in dit project ("nieuwe query-DTO's moeten `limit` overriden met `@Max(200)`"; de
basis-DTO cap't op `@Max(100)`). Een deel van de endpoints heeft die override wél gekregen
(requests/projects/planning/measurement-instruments), de rest niet — terwijl de portal overal
`limit: 200` hanteert.

## Advies
- Verhoog de cap in de gedeelde `PaginationQueryDto` naar 200 (of override consequent per DTO), zodat
  frontend en backend weer één contract hebben. Voeg een unit-/e2e-test toe die `limit=200` op elk
  gepagineerd endpoint controleert.
- Onafhankelijk daarvan: laat de portal een mislukte dropdown-query zichtbaar maken (foutstate i.p.v.
  lege lijst), zodat dit soort mismatches niet stil blijft.
