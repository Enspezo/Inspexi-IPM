# B-308 — Dubbelklik op "Versturen" verstuurt de offerte twee keer (2× klant-e-mail, 2× statuswijziging, 2× notificatie)

- **Testgeval:** BO-29
- **Actor / rol:** Backoffice / MANAGER
- **App:** Portal (:5173) + API (:3001) · org: inspexidemo
- **Severity:** S2 (ernstig — niet-idempotente klantcommunicatie; de klant krijgt de offerte dubbel)
- **Type:** concurrency / dubbelactie
- **Datum/tijd:** 2026-07-27 10:57

## Verwacht
"Idempotent: niet 2× verstuurd, geen dubbele mail." De knop hoort direct na de eerste klik disabled te
raken (of de backend hoort een tweede `send` op een al verstuurde offerte te weigeren).

## Werkelijk
Twee snelle klikken op **Versturen** in de verzendmodal leveren **twee** `POST …/send`-calls, beide
**201 Created**. De UI toont twee toasts "Offerte verstuurd".

Database-effect op OFF-2026-0003:

```
imp_audit_logs   → 2× UPDATE {"to":"VERSTUURD","from":"CONCEPT"}  (08:57:10.949, 08:57:10.949)
imp_notifications→ 2× OFFERTE_VERSTUURD                            (08:57:10.983, 08:57:10.988)
```

`sendQuote()` verstuurt per aanroep een e-mail naar de klant, dus de klant ontvangt de offerte
**tweemaal**. Een derde klik ~80 ms later werd wél genegeerd (de knop was toen disabled), dus het
kwetsbare venster is klein maar reëel — met een trage verbinding groeit het.

## Reproductie
1. Login `manager@inspexi-demo.nl`, open een CONCEPT-offerte met sjabloon onder de drempel.
2. Klik **Versturen** → verzendmodal.
3. Klik **twee keer snel achter elkaar** op de knop **Versturen** in de modal.
4. Twee toasts "Offerte verstuurd"; in Network twee `POST /api/v1/quotes/:id/send → 201`.

## Analyse / vermoedelijke oorzaak
De modalknop is niet gekoppeld aan `mutation.isPending` op het moment van de eerste klik (React-state
update komt pas na de render), en `QuotesService.sendQuote()` accepteert `CONCEPT` **én** `GOEDGEKEURD`
zonder te controleren of `sentAt` al gezet is. Er is dus noch client- noch serverzijdige idempotentie.

## Advies
- Zet de verzendknop synchroon op `disabled` bij `onClick` (of gebruik `mutation.isPending` + een
  `useRef`-guard).
- Serverzijdig: weiger een tweede `send` wanneer `sentAt` al gezet is en de status al `VERSTUURD` is
  (400 "Deze offerte is al verstuurd"), of maak `send` expliciet idempotent (geen tweede e-mail,
  geen tweede notificatie).

## Status
**Opgelost in WP-B5** (branch `fix/wp-b5-quote-chain`).
- Serverzijdig race-vrij: `sendQuote()` claimt éérst atomisch het verzendrecht via een conditionele `updateMany({ where: { id, orgId, sentAt: null, status: CONCEPT|GOEDGEKEURD } })`; alleen bij `count === 1` wordt gemaild. De verliezer krijgt 400 "Deze offerte is al verstuurd". Bij een mislukte verzending wordt de claim teruggedraaid zodat opnieuw versturen kan; de statusovergang → VERSTUURD blijft een geauditeerde update (exact één audit-rij, één notificatie, één e-mail).
- Clientzijdig: synchrone `useRef`-guard in de verzendmodal vóór de `await` (twee klikken in dezelfde render-batch worden nu al client-side gestopt).
- Zelfde patroon gecontroleerd op `POST /planning/:id/send-confirmation` en `POST /generated-documents/:id/request-signature`: beide zijn bewust herhaalbaar (handmatig opnieuw versturen resp. meerdere ondertekenaars) en hebben geen éénmalige `sentAt`-staat om op te claimen → niet gewijzigd, gedocumenteerd in de PR.
- "Opnieuw versturen" (expliciete resend na de eerste verzending) is bewust niet gebouwd — als open vraag opgenomen in de PR.
- Tests: parallelle `Promise.all`-unit-test (1× succes, 1× 400, e-mailmock exact 1×) + e2e-race-test tegen de echte database.
