# B-401 — Klantportaal: tab "Constateringen" crasht volledig (`finding.asset` bestaat niet meer)

- **Testgeval:** KL-08 (blokkeert KL-09 t/m KL-14 in de UI)
- **Actor / rol:** Klant (ClientUser, elke rol) — ook anoniem niet omzeilbaar
- **App:** Client-portal (:5174) · org: inspexidemo
- **Severity:** S1 (blokkerend — crash, kernfunctie onbruikbaar)
- **Type:** contractbreuk frontend↔backend (AssetNode-migratie)
- **Datum/tijd:** 2026-07-27 10:20

## Verwacht
Op de inspectiedetailpagina toont de tab **Constateringen** de lijst met constateringen, met per
constatering de asset/locatie, de status en de knop "Constatering oplossen" (KL-08/KL-09).

## Werkelijk
Zodra de tab geopend wordt, gooit `<FindingCard>` een `TypeError` en neemt de **hele pagina** over
via de ErrorBoundary:

```
Er is een onverwachte fout opgetreden
De pagina kon niet worden geladen. Probeer de pagina opnieuw te laden.
Cannot read properties of undefined (reading 'locationDescription')
```

De klant kan daardoor **geen enkele constatering inzien of oplossen** via het klantportaal — niet
op RAP-TEST-100, niet op TP-RAP-005, niet op TP-RAP-001. Het gebeurt bij élk inspectieplan dat
minstens één constatering heeft.

## Reproductie
1. Log in op `http://inspexidemo.localhost:5174` (bv. `tp-signer@klant.nl` / `Password123!`).
2. Open een inspectie met constateringen, bv.
   `/inspections/ce42f284-80a6-4b1c-8e07-fbc5cedd3cc2` (RAP-TEST-100) of
   `/inspections/ae4c8259-d5d2-4177-8d5f-2795e1867b8a` (TP-RAP-005).
3. Klik op de tab **Constateringen** (de teller naast de tab klopt wel: 3 resp. 1).
4. → foutkaart, tab blijft onbruikbaar; "Opnieuw proberen"/"Pagina herladen" herhaalt de crash.

Ook bereikbaar via het dashboard-blok "N openstaande constateringen → Bekijk".

## Bewijs
- Console (browser):
  `The above error occurred in the <FindingCard> component: at FindingCard (…/pages/inspections/components/findings-tab.tsx:116:3) at FindingsTab (…findings-tab.tsx:25:31) at InspectionDetailPage …`
- API is wél gezond: `GET /api/v1/client/inspections/{planId}/findings` → **HTTP 200**, en levert per
  constatering een veld **`assetNode`** (`{id, name, description}`) — er is géén veld `asset`.
- HTTP: geen 4xx/5xx; puur client-side.

## Analyse / vermoedelijke oorzaak
Bij de unified-AssetNode-migratie is de API-respons hernoemd van `asset` → `assetNode`
(`client-findings.service.ts` include `assetNode: { select: { id, name, description } }`), maar het
klantportaal is niet meegemigreerd. Twee bestanden lezen nog `finding.asset`:

- `apps/client-portal/src/pages/inspections/components/findings-tab.tsx:83`
  `const location = finding.locationDescription || finding.asset.locationDescription;`
- `apps/client-portal/src/pages/inspections/components/findings-tab.tsx:115` `{location} · {finding.asset.name}`
- `apps/client-portal/src/pages/inspections/components/finding-detail-modal.tsx:133-136` (idem —
  dus ook het detailscherm zou crashen zodra de lijst weer laadt)

Opvallend: het type `Finding` in het klantportaal kent kennelijk nog een `asset`-veld, waardoor
TypeScript dit niet heeft gevangen; de backend-selectie is los daarvan gewijzigd.

## Advies
1. Vervang in beide bestanden `finding.asset` door `finding.assetNode` en trek het TypeScript-type
   gelijk met de daadwerkelijke API-respons (`assetNode`, zonder `locationDescription` — dat veld
   zit niet in de select, dus gebruik `finding.locationDescription` met `?? null` als fallback).
2. Maak de veldtoegang defensief (`finding.assetNode?.name ?? '—'`) zodat een ontbrekende relatie
   nooit meer een hele pagina sloopt.
3. Zet een smoke-test (Vitest/Playwright) op de tab Constateringen — dit is de kernfunctie van het
   klantportaal en er is nu geen enkele test die 'm dekt.
