# B-403 — Klantverzoeken (herinspectie / nieuwe opdracht) zijn voor de staf onzichtbaar

- **Testgeval:** KL-21
- **Actor / rol:** Klant (ClientUser) → staf (BACKOFFICE/MANAGER)
- **App:** Client-portal (:5174) + Portal (:5173) + API (:3001) · org: inspexidemo
- **Severity:** S2 (ernstig — gouden pad breekt; commerciële aanvragen verdwijnen)
- **Type:** onvolledige functionaliteit / dead-end
- **Datum/tijd:** 2026-07-27 10:22

## Verwacht
KL-21: "Nieuw verzoek: herinspectie (plan + beschrijving + voorkeursdatum) → ClientRequest
PENDING_REQUEST; **staf ziet 'm**." Het klantportaal belooft dat ook letterlijk:
> "Uw aanvraag is ontvangen. De organisatie neemt deze in behandeling en koppelt terug."

## Werkelijk
De `ClientRequest` wordt correct aangemaakt (org uit subdomein, contact uit ClientAccess, status
`PENDING_REQUEST`), maar de organisatie kan er niet bij:

1. De enige controller op het model is `@Controller('client/requests')` — dus uitsluitend
   klant-endpoints (`GET /`, `POST /reinspection`, `POST /new-assignment`, `GET /:id`).
2. In `apps/portal/src` bestaat geen pagina/route voor klantverzoeken; alleen de lookup-configuratie
   ("Klantverzoek-types" / "Klantverzoek-statussen") is aanwezig, wat suggereert dat het beheer­scherm
   nog ontbreekt.
3. Er wordt **geen notificatie** gedispatcht (`imp_notifications` ongewijzigd na indienen).
4. De velden `handledBy`, `handledAt`, `responseNotes`, `resultingInspectionPlanId` bestaan wél in
   het model maar zijn door niets te vullen.

## Reproductie
1. Login klantportaal (`tp-signer@klant.nl` / `Password123!`), tab **Verzoeken** → "Nieuwe opdracht".
2. Onderwerp + omschrijving invullen → **Verzoek indienen** → bevestigingsscherm.
3. DB:
   ```sql
   select subject, status, org_id, created_at from imp_client_requests order by created_at desc limit 1;
   -- KL-21 herinspectie na herstel 🚀 | PENDING_REQUEST | f765ff41-… | 2026-07-27 10:22:13
   select type, created_at from imp_notifications order by created_at desc limit 1;  -- ongewijzigd
   ```
4. Zoek als staf: geen route en geen scherm.
   `grep -rn "client-requests\|clientRequests" apps/portal/src` → alleen lookup-labels.

## Bewijs
- HTTP: `POST /api/v1/client/requests/new-assignment` → 201.
- HTTP: `POST /api/v1/client/requests/reinspection` → 201.
- Code: `apps/api/src/modules/client-requests/client-requests.controller.ts` bevat uitsluitend
  `@Controller('client/requests')`; geen staf-controller op `ClientRequest`.
- Ook de seed-rij `1bfd858a-… "Verzoek om herinspectie na herstel"` (PENDING_REQUEST, 27-07) staat al
  weken in de wachtrij zonder dat iemand 'm kan zien.

## Analyse / vermoedelijke oorzaak
Zelfde patroon als B-402: de klantzijde van de PRD-14/fase-6-functionaliteit is af, de stafzijde
(wachtrij + afhandeling + notificatie) is niet gebouwd. Het domeinmodel is er al volledig op ingericht.

## Advies
1. Bouw een staf-endpoint + wachtrijscherm (`GET /client-requests` met filters op status/type,
   `PATCH /client-requests/:id` voor afhandelen → `handledBy/handledAt/responseNotes` en eventueel
   het aanmaken van een inspectieplan / aanvraag).
2. Dispatch bij indienen een notificatie naar BACKOFFICE/MANAGER (nieuw type, groep AANVRAGEN).
3. Tot die tijd: e-mail de organisatie in elk geval bij een nieuw verzoek, zodat er geen aanvraag
   stilletjes verdwijnt.

## Status
**Deels — mitigatie** (WP-B9, branch `fix/wp-b9-client-portal-mitigations`); de stafzijde
(wachtrij + afhandeling + in-app-notificatie) is **Epic 2** in
`docs/herstelplan/03-beslispunten-backlog.md` §C (beslissing D1, incl. architectuurkeuze route
A/B). Gedaan (adviespunt 3): bij élk nieuw klantverzoek (herinspectie én nieuwe opdracht) stuurt
`ClientRequestsService.notifyOrganization()` fire-and-forget een e-mail naar alle actieve
stafgebruikers met rol **ORG_ADMIN/MANAGER/BACKOFFICE** van de org (nieuwe
`ClientRequestEmailService` naar het voorbeeld van `repair-email.service.ts`; klant-invoer wordt
ge-escaped; geen ontvangers → Logger.warn). Een in-app `NotificationType` vergt een migratie en is
bewust doorgeschoven naar de epic. De bevestigingstekst in het klantportaal is eerlijk gemaakt:
"per e-mail aan de organisatie doorgegeven — wij nemen contact met u op" i.p.v. de suggestie van
een stafwachtrij. Punten 1 en 2 zijn bewust NIET gebouwd (epic).
