# B-404 — Klantportaal-ondertekening accepteert elke string als handtekening (geen `IsSafeDataImage`, geen 5 MB-limiet)

- **Testgeval:** KL-20
- **Actor / rol:** Klant (ClientUser met canSign)
- **App:** API (:3001), route `POST /client/documents/:id/sign` · org: inspexidemo
- **Severity:** S3 (matig — ontbrekende validatie; render-laag vangt het gelukkig af)
- **Type:** grenswaarde / ontbrekende invoervalidatie
- **Datum/tijd:** 2026-07-27 10:11

## Verwacht
KL-20: "Handtekening-payload > 5 MB of verkeerde data-URI → geweigerd (`IsSafeDataImage`, ≤ 5 MB,
`data:image/(png|jpeg|jpg|webp)`)". De publieke ondertekenroute doet dit ook keurig:

```
POST /api/v1/signature-requests/{uuid}/sign   {"signatureImage":"javascript:alert(1)"}
→ 400 "signatureImage moet een geldige base64 data-afbeelding zijn (image/png, image/jpeg of image/webp, max 5 MB)"
```

## Werkelijk
Dezelfde payloads worden via het **klantportaal** klakkeloos geaccepteerd en opgeslagen, en het
document gaat er zelfs door naar status `SIGNED`:

| payload | verwacht | werkelijk |
|---|---|---|
| `javascript:alert(1)` | 400 | **201** — opgeslagen, `documentFullySigned: true` |
| `data:image/png;base64,` + 7 000 000 tekens (~7 MB) | 400 | **201** — `length(signature_image) = 7 000 022` |
| `""` (leeg) | 400 | 400 ✔ (`signatureImage should not be empty`) |

Een "ondertekend" rapport kan dus een handtekening bevatten die geen afbeelding is, en één klant kan
met een handvol requests tientallen MB's in de database schrijven (de bodylimiet voor
`/api/v1/client/documents` staat bewust op 10 MB).

## Reproductie
```bash
TOK=$(curl -s -X POST -H 'Host: inspexidemo.localhost' -H 'Content-Type: application/json' \
  -d '{"email":"tp-signer@klant.nl","password":"Password123!"}' \
  http://localhost:3001/api/v1/client/auth/login | jq -r .data.accessToken)

curl -i -X POST -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $TOK" \
  -H 'Content-Type: application/json' \
  -d '{"signatureImage":"javascript:alert(1)","signerName":"Sander"}' \
  http://localhost:3001/api/v1/client/documents/5a525045-8106-47a8-a76d-ad298eba8d41/sign
# HTTP/1.1 201  {"success":true,"data":{"status":"SIGNED","documentFullySigned":true}}
```
```sql
select status, signature_image from imp_document_signatures where id='6ff35c85-…';
-- SIGNED | javascript:alert(1)
```

## Bewijs
- HTTP 201 op beide onveilige payloads (zie hierboven); 400 op dezelfde payload via
  `/signature-requests/:id/sign`.
- Code: `apps/api/src/modules/client-documents/dto.ts` →
  ```ts
  export class ClientSignDocumentDto {
    @IsString() @IsNotEmpty() signatureImage: string;   // ← geen @IsSafeDataImage(), geen @MaxLength
  }
  ```
  vs. `apps/api/src/modules/generated-documents/dto/generate-document.dto.ts:41` en
  `apps/api/src/modules/client-repair/dto/index.ts:68`, die `@IsSafeDataImage()` wél gebruiken.
- `apps/api/src/main.ts:59-66`: `/api/v1/client/documents` heeft een 10 MB-bodylimiet.

## Analyse / vermoedelijke oorzaak
`IsSafeDataImage` is bij het hardenen toegepast op `generated-documents` en `client-repair`, maar
`client-documents` (de klantportaal-route) is overgeslagen. De impact blijft beperkt doordat de
render-laag defensief is: `generated-documents.service.ts:278`
(`const safeImage = isSafeDataImage(sig.signatureImage) ? sig.signatureImage : null`) en
`pdf-generation.service.ts:112` neutraliseren de waarde alsnog — er is dus **geen** actieve
XSS-vector aangetoond. Wat wél overblijft: rommel in de audit trail (een "getekend" document met een
niet-renderbare handtekening) en ongelimiteerde opslag.

## Advies
1. Zet `@IsSafeDataImage()` op `ClientSignDocumentDto.signatureImage` (één regel; de validator
   bewaakt zowel het schema als de 5 MB).
2. Overweeg een DB-check/opruimscript op bestaande `imp_document_signatures.signature_image` die
   `isSafeDataImage` niet passeren.
3. Voeg een unit-test toe die voor álle drie de sign-DTO's dezelfde validator afdwingt.

`extends SignatureImageDto` laat de test falen — de "volgende vergeten route" kan dus niet meer).
