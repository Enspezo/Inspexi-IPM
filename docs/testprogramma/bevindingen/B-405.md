# B-405 — Eenmalige magic-link is niet atomair: gelijktijdig gebruik levert meerdere geldige sessies (TOCTOU)

- **Testgeval:** KL-02 (verkennende uitbreiding)
- **Actor / rol:** Klant (ClientUser) — wachtwoordloze login
- **App:** API (:3001), route `POST /client/auth/magic-link` · org: inspexidemo
- **Severity:** S3 (matig — verzwakt een beveiligingscontrole, geen extra rechten)
- **Type:** concurrency / race-conditie
- **Datum/tijd:** 2026-07-27 10:00 (opgemerkt), 10:03 (gereproduceerd)

## Verwacht
Een magic-link is eenmalig (`usedAt`). Sequentieel hergebruik wordt correct geweigerd:
`400 "Magic link ongeldig of verlopen"` (KL-02/KL-03 → PASS). Ook bij **gelijktijdige** verzilvering
zou er hooguit één sessie uitgegeven mogen worden.

## Werkelijk
Drie gelijktijdige verzilveringen van dezelfde ongebruikte link leveren **drie** succesvolle
logins (3× HTTP 201 met een eigen access- en refresh-token):

```
req1 HTTP 201  {"success":true, …accessToken…}
req2 HTTP 201  {"success":true, …accessToken…}
req3 HTTP 201  {"success":true, …accessToken…}
```

Het viel op tijdens KL-01: React StrictMode vuurt het effect in dev tweemaal af, en in het
netwerkoverzicht stonden **twee** `POST /client/auth/magic-link → 201 Created` naast elkaar op een
link die daarna als `usedAt` gemarkeerd stond.

## Reproductie
```bash
# token weer op ongebruikt zetten (testomgeving)
psql … -c "update imp_client_magic_links set used_at=null where token='tp-magic-geldig';"

for i in 1 2 3; do
  curl -s -o /tmp/race$i.txt -w "req$i HTTP %{http_code}\n" -X POST \
    -H 'Host: inspexidemo.localhost' -H 'Content-Type: application/json' \
    -d '{"token":"tp-magic-geldig"}' \
    http://localhost:3001/api/v1/client/auth/magic-link &
done; wait
grep -o '"success":[a-z]*' /tmp/race1.txt /tmp/race2.txt /tmp/race3.txt
# alle drie: "success":true
```

Sequentieel (dus ná het wegschrijven van `usedAt`) gedraagt de route zich wél correct:
`{"token":"tp-magic-gebruikt"}` → `400 "Magic link ongeldig of verlopen"`.

## Bewijs
- 3× HTTP 201 op één eenmalige token (zie repro); daarna `used_at` gevuld.
- Browser-netwerklog KL-01: `POST /api/v1/client/auth/magic-link → 201 Created` (2×) op
  `demo-klant-magic`.
- Code `apps/api/src/modules/client-auth/client-auth.service.ts:180-215` — lees-dan-schrijf zonder
  conditionele update:
  ```ts
  const link = await this.prisma.clientMagicLink.findUnique({ where: { token } });
  if (!link || link.usedAt || link.expiresAt < new Date()) throw new BadRequestException(…);
  …
  await this.prisma.$transaction([
    this.prisma.clientMagicLink.update({ where: { id: link.id }, data: { usedAt: new Date() } }),
    …
  ]);
  ```
  De transactie beschermt alleen het schrijven, niet de check.

## Analyse / vermoedelijke oorzaak
Klassieke TOCTOU: tussen `findUnique` (check) en `update` (consume) zit geen atomaire garantie. Elke
gelijktijdige aanvraag ziet `usedAt === null`. Praktische impact is beperkt — de aanvaller heeft de
link sowieso nodig en krijgt dezelfde rechten als de rechtmatige gebruiker — maar de "eenmalig"-
garantie waar de link zijn beveiligingswaarde aan ontleent, houdt onder gelijktijdigheid geen stand.
Dezelfde constructie zit in `resetPassword()` (`client-auth.service.ts:...`, ook `if (link.usedAt)`),
waar het zwaarder weegt: twee partijen kunnen dan gelijktijdig een wachtwoord zetten.

## Advies
Consumeer de link met een conditionele update en beslis op het aantal geraakte rijen:
```ts
const { count } = await this.prisma.clientMagicLink.updateMany({
  where: { id: link.id, usedAt: null, expiresAt: { gt: new Date() } },
  data: { usedAt: new Date() },
});
if (count === 0) throw new BadRequestException('Magic link ongeldig of verlopen');
```
Pas dezelfde patch toe op `register()` en `resetPassword()`.

## Status
**Opgelost** (WP-C2, branch `fix/wp-c2-client-hygiene`). Nieuwe private helper
`consumeMagicLink()` in `client-auth.service.ts`: één conditionele
`updateMany({ where: { id, usedAt: null, expiresAt: { gt: now } }, data: { usedAt: now } })` en
beslissen op `count === 0` — de database serialiseert de row-update, dus onder gelijktijdigheid
wint er precies één request. Toegepast op alle drie de plekken:
- `validateMagicLink()` — consume ná de org-/grant-checks (een gefaalde toegangscheck verbrandt de
  link niet); verliezers krijgen de bestaande generieke 400 "Magic link ongeldig of verlopen".
- `register()` — de link blijft BEWUST open tussen validatie en registratie (ontwerp); het
  definitieve consumeren (mét `clientUserId`) is nu atomisch; de verliezer krijgt 400 en géén sessie.
- `resetPassword()` (woog het zwaarst) — consume ín dezelfde interactieve transactie als het
  wachtwoord-schrijven + sessie-revoke: twee gelijktijdige resets kunnen nooit allebei een
  wachtwoord zetten, en bij een gefaalde schrijfactie rolt ook het consumeren terug.
Race-e2e (`client-portal.e2e-spec.ts`): drie gelijktijdige verzilveringen via `Promise.all` →
precies 1× 201 en 2× 400. Unit-specs dekken winnaar/verliezer per flow.
