# B-406 — Klantportaal dringt aan op ondertekenen dat de klant niet mág (en er is geen staf-flow die het recht toekent)

- **Testgeval:** KL-18 (en KL-16/KL-17)
- **Actor / rol:** Klant — VIEWER (`tp-viewer@klant.nl`) én SIGNER (`tp-signer@klant.nl`)
- **App:** Client-portal (:5174) + API (:3001) · org: inspexidemo
- **Severity:** S3 (matig — autorisatie is correct, maar de UX is misleidend en de flow onvolledig)
- **Type:** autorisatie-UX / ontbrekende beheerfunctie
- **Datum/tijd:** 2026-07-27 10:07

## Verwacht
KL-18: "Ondertekenen door een VIEWER-client (geen SIGNER-rol) → **geweigerd/knop afwezig**."
Een klant die niet mag tekenen krijgt de actie niet aangeboden.

## Werkelijk
De backend weigert correct (**HTTP 403** — "Geen recht om dit document te ondertekenen"), maar de UI
doet er alles aan om de klant tóch die kant op te sturen:

1. Het **dashboard** toont voor de VIEWER het blok *"Actie vereist — Inspectierapport ondertekenen —
   TP Goedgekeurde inspectie …"* met een "Bekijk →"-link.
2. De documentpagina toont een volledig actieve knop **"Ondertekenen"**.
3. De klant opent de modal, **tekent zijn handtekening**, vinkt "Ik ga akkoord met de inhoud" aan en
   krijgt pas dán de melding *"Geen recht om dit document te ondertekenen"*.

Erger: dit geldt óók voor `tp-signer@klant.nl` (ClientAccess-rol **SIGNER**). Ondertekenen vereist
namelijk een **per-plan** `InspectionClientAccess.canSign`, en die rij wordt in de hele codebase
uitsluitend aangemaakt door het magic-link-pad (`client-auth.service.ts:146`). Er is **geen
staf-endpoint en geen portal-scherm** waarmee de organisatie dat recht kan toekennen — `grep -rn
"inspectionClientAccess" apps/api/src` geeft alleen client-auth + de twee leesplekken in
`client-inspections.service.ts`. Voor TP-RAP-005 bestond die grant niet, dus **geen enkele klant**
kon dat rapport in het portaal ondertekenen.

## Reproductie
1. Login `tp-viewer@klant.nl` / `Password123!` op `inspexidemo.localhost:5174`.
2. Dashboard → "Actie vereist: Inspectierapport ondertekenen" → **Bekijk →**.
3. Knop **Ondertekenen** → teken in het canvas → **Handtekening opslaan** → vink akkoord aan →
   **Ondertekenen**.
4. → rode melding *"Geen recht om dit document te ondertekenen"*.
5. Herhaal met `tp-signer@klant.nl` → **identiek resultaat** (403), ondanks rol SIGNER.

## Bewijs
- HTTP: `POST /api/v1/client/documents/5a525045-…/sign` → **403 Forbidden**
  (`{"success":false,"message":"Geen recht om dit document te ondertekenen"}`).
- Code `apps/api/src/modules/client-inspections/client-inspections.service.ts:93-106`
  (`assertSignAccess` eist `inspectionClientAccess.canSign === true` op het specifieke plan).
- DB: `imp_inspection_client_access` bevat uitsluitend rijen voor plan
  `ce42f284-…` (RAP-TEST-100, aangemaakt door de geseede magic-links) — niets voor TP-RAP-005.
- Na het handmatig toevoegen van een `can_sign = true`-rij verloopt KL-16/KL-17 wél vlekkeloos
  (document → SIGNED), wat bevestigt dat alleen de rechtentoekenning ontbreekt.

## Analyse / vermoedelijke oorzaak
Twee losse gaten die elkaar versterken:
- De "Actie vereist"/knop-logica leidt af van een openstaande `CLIENT`-handtekening op een plan
  waar de klant **inzage** heeft, zonder `canSign` te checken; de rol uit `ClientAccess`
  (VIEWER/SIGNER/ADMIN) speelt in het geheel geen rol bij ondertekenen.
- `InspectionClientAccess` kan alleen via een magic link ontstaan, en magic links kunnen alleen door
  de seed worden aangemaakt (`clientMagicLink.create` komt in de API verder alleen in
  `forgotPassword()` voor). De bedoelde route voor staf is kennelijk de publieke
  `/sign/:requestId`-link per e-mail (B-408) — maar het portaal biedt de actie ook aan.

## Advies
1. Laat de API per document een `canSign`-vlag meegeven en verberg dan de knop + het
   dashboard-item wanneer die false is (met uitleg: "ondertekening verloopt via de link in uw e-mail").
2. Kies expliciet: óf `ClientAccess.role = SIGNER/ADMIN` wordt een geldige bron van tekenrecht, óf
   er komt een staf-actie ("klant uitnodigen om te ondertekenen") die de
   `InspectionClientAccess`-grant + magic link aanmaakt. Nu is de rol puur decoratief.
3. Verplaats de rechtencheck naar vóór het handtekening-canvas, zodat niemand eerst tekent en dan
   pas te horen krijgt dat het niet mag.
