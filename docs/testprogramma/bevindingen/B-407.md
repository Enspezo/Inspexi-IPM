# B-407 — Ontbrekende lengte-/datumvalidatie op klantportaal-DTO's (resolutie-omschrijving, verzoekdatum)

- **Testgeval:** KL-12 (+ verkennende uitbreidingen op KL-21)
- **Actor / rol:** Klant (ClientUser)
- **App:** API (:3001) · org: inspexidemo
- **Severity:** S3 (matig — vervuilde data, geen directe schade)
- **Type:** grenswaarde / ontbrekende invoervalidatie
- **Datum/tijd:** 2026-07-27 10:18

## Verwacht
- KL-12: "Beschrijving 4001 tekens → geweigerd (`@MaxLength(4000)`)."
- Een voorkeursdatum voor een herinspectie ligt in de toekomst; een omschrijving heeft een zinnige
  minimumlengte (de UI eist zelf 10 tekens).

De herstel-tegenhanger doet dit wél goed: `RepairResolveDto.description` heeft `@MaxLength(4000)`
én NL-meldingen (`apps/api/src/modules/client-repair/dto/index.ts:29-34`).

## Werkelijk
| invoer | endpoint | verwacht | werkelijk |
|---|---|---|---|
| `description` = 4 001 × "A" | `POST /client/findings/:id/resolve` | 400 | **201** |
| `description` = 100 000 × "B" | `POST /client/findings/:id/resolve` | 400 | **201** (opgeslagen) |
| `preferredDate` = `1999-01-01` | `POST /client/requests/reinspection` | 400 of waarschuwing | **201** |
| `description` = `"x"` (1 teken) | `POST /client/requests/reinspection` | 400 | **201** |
| `preferredDate` = `"gisteren"` | `POST /client/requests/reinspection` | 400 | 400 ✔ (ISO-8601-check) |

## Reproductie
```bash
TOK=$(curl -s -X POST -H 'Host: inspexidemo.localhost' -H 'Content-Type: application/json' \
  -d '{"email":"tp-signer@klant.nl","password":"Password123!"}' \
  http://localhost:3001/api/v1/client/auth/login | jq -r .data.accessToken)

python3 -c "import json;print(json.dumps({'description':'A'*4001}))" > /tmp/long.json
curl -i -X POST -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $TOK" \
  -H 'Content-Type: application/json' --data-binary @/tmp/long.json \
  http://localhost:3001/api/v1/client/findings/28d1e69f-381e-424b-a056-2d8a2dfbe5cf/resolve
# HTTP/1.1 201

curl -i -X POST -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $TOK" \
  -H 'Content-Type: application/json' \
  -d '{"inspectionPlanId":"ce42f284-80a6-4b1c-8e07-fbc5cedd3cc2","description":"x","preferredDate":"1999-01-01"}' \
  http://localhost:3001/api/v1/client/requests/reinspection
# HTTP/1.1 201
```

## Bewijs
- HTTP 201 op alle bovenstaande gevallen (zie repro).
- Code `apps/api/src/modules/client-findings/dto.ts`:
  ```ts
  export class ResolveFindingDto {
    @IsOptional() @IsString() description?: string;   // ← geen @MaxLength
  }
  ```
- Code `apps/api/src/modules/client-requests/dto.ts`: `description` heeft alleen
  `@IsString() @IsNotEmpty()`; `preferredDate` alleen `@IsDateString()` (geen ondergrens).
- De frontend dwingt "minimaal 10 tekens" wél af, maar dat is puur client-side (KL-22 → PASS).

## Analyse / vermoedelijke oorzaak
Twee klantportaal-modules zijn bij de hardening-ronde overgeslagen; `client-repair` (PRD-14, nieuwer)
heeft de validatie wél. `description` is een `Text`-kolom, dus er is geen DB-limiet die het opvangt —
een klant kan willekeurig grote teksten opslaan (tot de 1 MB bodylimiet per request, herhaalbaar).

## Advies
1. `@MaxLength(4000)` op `ResolveFindingDto.description` (met NL-melding, net als bij
   `RepairResolveDto`).
2. `@MinLength(10)` + `@MaxLength(4000)` op `ClientRequest`-omschrijvingen, zodat backend en UI
   dezelfde regel hanteren.
3. Voor `preferredDate`: minimaal een `@MinDate(new Date())`-equivalent of een expliciete
   businessregel ("voorkeursdatum in het verleden wordt genegeerd") — nu belandt 1999 gewoon in de
   wachtrij.
