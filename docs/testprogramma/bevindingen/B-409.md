# B-409 — Anonimisering van de hersteller is inconsistent: de herstelverklaring noemt hem wél bij naam in het klantportaal

- **Testgeval:** KL-14
- **Actor / rol:** Klant (ClientUser met inzage)
- **App:** Client-portal (:5174) · org: inspexidemo
- **Severity:** S3 (matig — privacy-/ontwerpinconsistentie, geen technisch defect)
- **Type:** inconsistente implementatie van een expliciete ontwerpbeslissing
- **Datum/tijd:** 2026-07-27 10:26

## Verwacht
KL-14: "Klant-zijde: kan de klant zien **wie** herstelde? → Nee — klant ziet nooit invullergegevens
(staf wél)." Dat is ook expliciet zo vastgelegd in de code:

```ts
// Anonimiteit (PRD-14 §14.3 besluit 4): bij herstel-flow-resoluties (REPORTED/CONFLICT)
// mag het klantportaal nooit zien wíe herstelde — ook niet wanneer een ingelogde klant
// de hersteller was. Staf ziet de invullergegevens wél.
```
(`apps/api/src/modules/client-findings/client-findings.service.ts`)

## Werkelijk
De constatering-API doet dit correct: `resolvedByClientUserId: null` en `resolvedByClientUser: null`
voor een REPORTED-resolutie. Maar de **Documenten-tab** van diezelfde inspectie lekt precies dezelfde
informatie:

- Kaartje in de documentenlijst: `Hersteller · Pieter Hersteller · 25 juli 2026`
- Documentvoorbeeld (HTML, in het klantportaal gerenderd):
  `Ingevuld door: Pieter Hersteller (TP Installatietechniek)`
- Handtekeningenpaneel: `Hersteller — Pieter Hersteller — Getekend op 25 juli 2026`
- Ook in de gedownloade PDF (`GET /client/documents/:id/download` → HTTP 200, `application/pdf`).

De klant die op de constatering geen naam te zien krijgt, ziet 'm dus één tab verderop wél.

## Reproductie
1. Login klantportaal (`tp-signer@klant.nl` / `Password123!`).
2. Open `/inspections/ce42f284-80a6-4b1c-8e07-fbc5cedd3cc2` (RAP-TEST-100).
3. API-controle constatering (anoniem):
   ```
   GET /api/v1/client/findings/ed5a7da5-e35d-49fd-b5a6-c05399239684
   → resolutions[0] = { statusCode:"REPORTED", resolvedByClientUserId:null, resolvedByClientUser:null }
   ```
4. Tab **Documenten** → HERSTELVERKLARING → **Bekijken** → "Ingevuld door: Pieter Hersteller
   (TP Installatietechniek)".

## Bewijs
- Klant-API constatering: `resolvedByClientUserId: null` (zie stap 3).
- Staf-API `GET /api/v1/findings/ed5a7da5-…` toont bewust wél
  `repairSession: { contactName:"Pieter Hersteller", companyName:"TP Installatietechniek",
  email:"hersteller@tp-installatie.nl", accessType:"ANONYMOUS" }` — dat deel werkt zoals bedoeld.
- Klantportaal-documentvoorbeeld toont naam + bedrijf; PDF-download 200 OK (72 kB).

## Analyse / vermoedelijke oorzaak
De anonimisering is als serializer-laag op `client-findings.getDetail` gebouwd. De herstelverklaring
is een `GeneratedDocument` waarvan de HTML de invullergegevens bevat (template
`herstelverklaring.template.ts`), en `client-documents.getDetail` geeft die HTML plus de
`signatures[]` (met `signerName`) ongefilterd door. Er is dus geen kwaadaardig lek, maar wel een
tegenstrijdigheid tussen twee schermen van hetzelfde portaal.

Kanttekening: voor een **verklaring** is het benoemen van de ondertekenaar juridisch juist logisch.
De vraag is dus welke van de twee schermen het beleid moet volgen — dat is een productbeslissing,
niet een bug in één regel code.

## Advies
1. Maak de beslissing expliciet in PRD-14 §14.3: geldt de anonimiteit alleen voor de
   constatering-weergave, of ook voor documenten?
2. Als de anonimiteit leidend is: filter in `client-documents` de HERSTELVERKLARING-signatures
   (`signerName`) en render een geanonimiseerde variant van de HTML voor het klantportaal.
3. Als de verklaring leidend is: laat dan ook bij de constatering zien dat er een ondertekende
   herstelverklaring is met een benoemde hersteller — nu wekt het klantportaal ten onrechte de
   indruk dat die informatie afgeschermd is.
