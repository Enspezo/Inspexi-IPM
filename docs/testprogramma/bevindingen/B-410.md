# B-410 — Herstelportaal toont classificaties zonder betekenis (grijs, geen label, `isCritical: false`) bij een plan zonder inspectietemplate

- **Testgeval:** PUB-07 (waargenomen tijdens PUB-07 t/m PUB-14)
- **Actor / rol:** Anonieme hersteller
- **App:** Client-portal (:5174) `/herstel` + API (:3001) · org: inspexidemo
- **Severity:** S4 (cosmetisch — de "Kritiek"-badge en de businesslogica kloppen wél)
- **Type:** ontbrekende fallback / degradatie
- **Datum/tijd:** 2026-07-27 10:37

## Verwacht
De hersteller ziet per constatering de ernstclassificatie zoals die in de organisatie geconfigureerd
is: `C1 — Gevaarlijk — direct herstellen` in rood (`#DC2626`, `isCritical = true`), `C2 — Onveilig —
herstel aanbevolen` in oranje, enz.

## Werkelijk
Alle classificaties komen terug als kale code, standaardgrijs en niet-kritiek:

```json
"summary": [
  { "code": "C1", "label": "C1", "color": "#666666", "isCritical": false, "openCount": 1 },
  { "code": "C2", "label": "C2", "color": "#666666", "isCritical": false, "openCount": 1 },
  { "code": "C3", "label": "C3", "color": "#666666", "isCritical": false, "resolvedCount": 1 }
],
"findings": [
  { "isCritical": true,
    "classification": { "code": "C1", "name": "C1", "color": "#666666", "isCritical": false } , … }
]
```

Terwijl in de database staat:

```sql
select o.code, o.name, o.is_critical, o.color from imp_classification_options o …;
-- C1 | Gevaarlijk — direct herstellen | t | #DC2626
-- C2 | Onveilig — herstel aanbevolen  | f | #D97706
-- C3 | Verbetering mogelijk           | f | #CA8A04
```

Merk op dat `finding.isCritical` (het gedenormaliseerde veld) wél `true` is en dat de UI daarop de
badge **"Kritiek"** toont — de hersteller wordt dus niet misleid over de urgentie, maar mist de
omschrijving en de kleurcodering. Ook de herstelverklaring krijgt hierdoor een grijze C1-badge
(`<span class="badge" style="background: #666666">C1</span>`).

## Reproductie
```bash
curl -s -X POST -H 'Host: inspexidemo.localhost' -H 'Content-Type: application/json' \
  -d '{"referenceNumber":"RAP-TEST-100","postalCode":"1012AB"}' \
  http://localhost:3001/api/v1/client/repair/lookup | python3 -m json.tool | head -60
```
Of in de UI: `http://inspexidemo.localhost:5174/herstel` → `RAP-TEST-100` / `1012 ab` →
blok **Samenvatting** toont drie grijze bolletjes met alleen "C1", "C2", "C3".

## Bewijs
- API-respons hierboven (`color: "#666666"`, `label` = `code`, `isCritical: false`).
- DB-waarden van `imp_classification_options` (zie hierboven).
- `select inspection_template_id from imp_inspection_plans where reference_number='RAP-TEST-100';`
  → **NULL**.
- Code `client-repair.service.ts:277-278`:
  `const classificationModel = plan.inspectionTemplate?.classificationModel ?? null;` — en
  `getMainClassification(values, null)` valt terug op code-only defaults.

## Analyse / vermoedelijke oorzaak
Het classificatiemodel wordt uitsluitend via `InspectionPlan.inspectionTemplate.classificationModel`
opgezocht. `inspectionTemplateId` is nullable, en het testplan RAP-TEST-100 heeft er geen — dan valt
alles terug op de neutrale default. Dat is in dit geval deels een **fixture-tekortkoming** (het
seed-plan mist een template), maar de fallback is te ruw: de organisatie heeft precies één
classificatiemodel met deze codes, en `Finding.isCritical` bevat het antwoord al.

## Advies
1. Val terug op `Finding.isCritical` wanneer het classificatiemodel onbekend is, zodat
   `classification.isCritical` nooit `false` beweert terwijl de constatering kritiek is.
2. Zoek het classificatiemodel eventueel op via `normTypeCode`/org-default als het plan geen
   template heeft, zodat labels en kleuren wél kloppen.
3. Geef het seed-plan `RAP-TEST-100` een `inspectionTemplateId`, zodat de fixture het normale pad
   test in plaats van het fallback-pad.
