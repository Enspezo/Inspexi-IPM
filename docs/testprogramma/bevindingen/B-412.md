# B-412 — Klant ziet inspecties die nog niet gereviewd/goedgekeurd zijn, inclusief hun constateringen

- **Testgeval:** KL-08 (verkennende uitbreiding; raakt risicogebied R3)
- **Actor / rol:** Klant (ClientUser, alle rollen)
- **App:** Client-portal (:5174) + API (:3001) · org: inspexidemo
- **Severity:** S3 (matig — compliance-vraag, geen technisch defect)
- **Type:** ontbrekende statusfilter / vier-ogen-principe
- **Datum/tijd:** 2026-07-27 10:05

## Verwacht
Masterplan §2, risico **R3**: "Inspectie vier-ogen-review-gate — *niet-gereviewd rapport naar klant =
compliance-risico*". De organisatie hanteert `Organization.inspectionReviewEnabled` (default `true`)
zodat een plan pas ná menselijke review naar `completed`/`approved` mag. De verwachting is dat de
inhoud van een nog niet gereviewde inspectie ook niet bij de klant terechtkomt.

## Werkelijk
Het klantportaal toont **alle** inspecties van het gekoppelde contact, ongeacht status. In deze run
zag `tp-signer@klant.nl` onder "Mijn inspecties":

| Rapportnummer | Status in DB | Getoond als |
|---|---|---|
| TP-RAP-001 | `pending_review` | **Wacht op review** |
| TP-RAP-002 | `planned` | Gepland |
| TP-RAP-003 | `reviewed` | Beoordeeld |
| TP-RAP-004 / 005 | `approved` | Goedgekeurd |
| TP-RAP-007 | `cancelled` | Geannuleerd |
| RAP-TEST-100 | `completed` | Afgerond |

Op TP-RAP-001 (`pending_review`) is het detailscherm volledig toegankelijk: omschrijving,
statusbalk, en het blok *"Constateringen gevonden — 1 constatering totaal · 1 openstaand"* met de
link "Constateringen bekijken →". De onderliggende API levert die constateringen ook daadwerkelijk
(`GET /client/inspections/{id}/findings` → 200 met de volledige constatering, inclusief
`shortDescription`, `longDescription` en classificatie).

Dat de tab zelf momenteel crasht (B-401) verhult dit alleen maar; via de API is de inhoud gewoon
beschikbaar.

## Reproductie
1. Login klantportaal (`tp-signer@klant.nl` / `Password123!`) op `inspexidemo.localhost:5174`.
2. **Inspecties** → "TP Concept-inspectie (draft)" (Ref. TP-RAP-001, badge *Wacht op review*).
3. Overzicht toont volledige details + "1 constatering totaal · 1 openstaand".
4. API-controle:
   ```
   GET /api/v1/client/inspections/0c46d844-ceaf-409b-8f49-31c5782d0ba2/findings   → 200, 1 finding
   ```
5. DB: `select status from imp_inspection_plans where reference_number='TP-RAP-001';` → `pending_review`.

## Bewijs
- Zie stap 3/4 hierboven; HTTP 200, geen enkele statusgate.
- Code `apps/api/src/modules/client-inspections/client-inspections.service.ts:114-116`:
  ```ts
  return this.prisma.inspectionPlan.findMany({
    where: { orgId: org, deletedAt: null, OR: or },   // ← geen statusCode-filter
  ```
  Ook `detail()` en de findings-query filteren nergens op planstatus.
- Ter contrast: de vier-ogen-gate is wél geïmplementeerd in `inspection-plans.service.update()` en
  in `sync.service` (`assertPlanReviewGate`) — dus alleen op statusovergangen, niet op zichtbaarheid.

## Analyse / vermoedelijke oorzaak
De review-gate is ontworpen als een *transitie*-gate (plan mag niet naar completed/approved zonder
review). Het klantportaal is los daarvan gebouwd op "alles van mijn contact", waardoor de klant ook
concept- en review-fase-materiaal ziet. Voor plannings- en statusinformatie is dat waarschijnlijk
gewenst (de klant wil zien wanneer de inspecteur komt); voor **constateringen en documenten** van een
nog niet beoordeeld rapport is het minstens discutabel.

## Advies
1. Maak expliciet welke planstatussen klant-zichtbaar zijn. Voorstel: metadata (titel, adres, datum,
   status) altijd; **constateringen en documenten** pas vanaf `reviewed`/`approved`.
2. Voeg dat filter toe in `client-inspections.service` (lijst + detail + findings) en in
   `client-documents`, zodat het niet van de UI afhangt.
3. Toon voor niet-vrijgegeven inspecties een nette placeholder ("het rapport wordt nog gecontroleerd")
   in plaats van de constateringenteller.
