# B-502 — SUPERUSER op een org-subdomein krijgt platform-brede data: geen tenant-scoping per subdomein

- **Testgeval:** SU-14 (ook zichtbaar bij SU-13)
- **Actor / rol:** Superuser / SUPERUSER
- **App:** Portal (:5173) + API (:3001) · elk org-subdomein
- **Severity:** S2 (ernstig — verkeerde scoping, nodigt uit tot mutaties in de verkeerde org)
- **Type:** autorisatie / multi-tenant scoping
- **Datum/tijd:** 2026-07-27 13:20

## Verwacht
`02-actor-superuser.md` SU-14: "Als SUPERUSER data van 2 orgs naast elkaar bekijken → **correcte scoping
per subdomein; geen vermenging**." Het subdomein bepaalt de tenantcontext (`TenantMiddleware` vult
`req.tenant.orgId`), dus op `nieuweklant.localhost` hoort de SUPERUSER de data van *Nieuwe Klant BV* te zien
— zeker op een pagina met de kop "Beheer de gebruikers van **uw organisatie**".

## Werkelijk
De org-scope wordt uitsluitend uit **`user.orgId`** afgeleid (`orgScope(user)` geeft voor een SUPERUSER
`{}` = géén filter). De tenantcontext van het subdomein wordt genegeerd. Gevolg: op élk org-subdomein
ziet de SUPERUSER de records van **alle** organisaties door elkaar, onder de branding en de koptekst van
de bezochte org.

- `nieuweklant.localhost:5173/users` (org met **0** gebruikers) toont **19** gebruikers uit 6 organisaties.
- `testbedrijf.localhost:5173/contacts` toont de relaties van `inspexidemo`, `inspeximix`,
  `inspexicompleet`, `inspexibasis` én `testbedrijf` in één lijst, zonder org-kolom.

Er is geen enkele visuele aanwijzing bij welke organisatie een rij hoort; de kop zegt "uw organisatie".

## Reproductie
1. Log in als `superuser@inspexi.nl` op `http://nieuweklant.localhost:5173` (org zonder gebruikers).
2. Ga naar **Organisatie → Gebruikers**.
3. Idem: log in op `http://testbedrijf.localhost:5173` en open **Relaties**.

API-niveau (zelfde token, alleen de Host-header verschilt):

```bash
TOK=<superuser accessToken>
curl -s -H 'Host: nieuweklant.localhost' -H "Authorization: Bearer $TOK" \
  http://localhost:3001/api/v1/users | python3 -c 'import sys,json;d=json.load(sys.stdin);print(len(d["data"]))'
# → 19  (org nieuweklant heeft 0 gebruikers)

curl -s -H 'Host: nieuweklant.localhost' -H "Authorization: Bearer $TOK" \
  'http://localhost:3001/api/v1/contacts?limit=5'
# → relaties met "orgId":"f765ff41-…" (= inspexidemo), niet nieuweklant
```

## Analyse / vermoedelijke oorzaak
`orgScope(user)` (`apps/api/src/common/utils/`) geeft voor een user zonder `orgId` (SUPERUSER) een lege
where-clausule terug. Alle listing-services spreiden dat in hun `where`. De `TenantContext` uit het
subdomein (`req.tenant.orgId`) wordt daarbij nergens meegewogen, terwijl `TenantGuard` die context wél
kent. Zie ook B-503: dezelfde oorzaak maakt aanmaken op een org-subdomein onmogelijk (500).

## Advies
Laat `orgScope()` (of een variant `orgScopeFor(user, tenant)`) voor een SUPERUSER terugvallen op
`tenant.orgId` zodra die gezet is, en alleen op het superuser-domein (`mijn.…`) platform-breed lezen.
Toon platform-brede lijsten bovendien altijd met een expliciete organisatie-kolom.

## Status
**Opgelost** in WP-B3 (PR [#141](https://github.com/Enspezo/Inspexi-IPM/pull/141), branch `fix/wp-b3-superuser-scoping`).
Beslissing D2 — *het subdomein bepaalt de scope* — is doorgevoerd op het ene punt dat
`user` én `tenant` samen ziet: de `TenantGuard` zet voor een SUPERUSER op een org-subdomein
de tenant-org als effectieve `orgId` op de request-user. Daarmee scopen álle downstream
consumenten (`orgScope`/`requireOrg`/`user.orgId`, incl. config-modules die nooit `orgScope`
gebruikten) automatisch op de bezochte org; op `mijn.*` en onbekende hosts blijft de
SUPERUSER platform-breed lezen. Nieuwe expliciete helpers `orgScopeFor(user, tenant)` /
`requireOrgFor(user, tenant)` zijn toegevoegd (tenant-matrix unit-getest); e2e-dekking in
`apps/api/test/superuser-scoping.e2e-spec.ts` (Host-header-matrix `GET /users` / `GET /contacts`).
*Restpunt (bewust buiten scope):* de organisatie-kolom op platform-brede lijsten op `mijn.*`.
