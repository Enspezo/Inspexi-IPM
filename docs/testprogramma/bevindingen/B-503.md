# B-503 — HTTP 500 zodra een SUPERUSER op een org-subdomein een record aanmaakt (orgId is null)

- **Testgeval:** SU-14 (verkennende afwijking tijdens SU-13/SU-14)
- **Actor / rol:** Superuser / SUPERUSER
- **App:** API (:3001) · elk org-subdomein · zichtbaar in Portal (:5173)
- **Severity:** S2 (ernstig — 500 op een gewone actie; orakel §3 "geen 500")
- **Type:** foutafhandeling / multi-tenant scoping
- **Datum/tijd:** 2026-07-27 13:25

## Verwacht
Geen 500 op geldige invoer. Ofwel het record wordt in de organisatie van het subdomein aangemaakt,
ofwel de API weigert het netjes ("kies eerst een organisatie", 400) — maar nooit een
`Internal server error`.

## Werkelijk
`POST /contacts` als SUPERUSER op een org-subdomein geeft **HTTP 500**. De UI toont daarbij alleen de
generieke foutmelding; er wordt niets aangemaakt. De SUPERUSER heeft `orgId = null`, en de service
schrijft die null in de verplichte FK-kolom `org_id`.

Dit is meteen de tweede helft van het onboarding-probleem: de SUPERUSER ziet op een org-subdomein wél
alle knoppen ("Relatie aanmaken", "+ Nieuw"), maar élke create loopt op een 500 uit.

## Reproductie
```bash
TOK=<superuser accessToken>
curl -s -o /tmp/r.txt -w '%{http_code}\n' -X POST \
  -H 'Host: nieuweklant.localhost' -H "Authorization: Bearer $TOK" \
  -H 'Content-Type: application/json' \
  -d '{"type":"COMPANY","companyName":"SU14 Scope Test"}' \
  http://localhost:3001/api/v1/contacts
cat /tmp/r.txt
```

Of via de UI: log als `superuser@inspexi.nl` in op `http://nieuweklant.localhost:5173`,
**Relaties → Relatie aanmaken**, vul een bedrijfsnaam in en sla op.

## Bewijs
```
HTTP 500
{"success":false,"message":"Internal server error",
 "requestId":"546cdde9-c6a3-48ec-8b25-b81ae9d70a37","statusCode":500}
```
Data onveranderd (geverifieerd):
```sql
SELECT id, org_id, company_name FROM imp_contacts WHERE company_name='SU14 Scope Test';
-- 0 rows
```

## Analyse / vermoedelijke oorzaak
De create-services nemen `user.orgId` over als `orgId`. Voor een SUPERUSER is dat `null`, wat de
`NOT NULL`/FK-constraint op `imp_contacts.org_id` schendt → onafgevangen Prisma-fout → 500.
Zelfde grondoorzaak als B-502 (subdomein-tenantcontext wordt niet gebruikt).

## Advies
Val voor een SUPERUSER terug op `tenant.orgId` bij creates (en weiger met een NL 400
"Kies eerst een organisatie" wanneer er geen tenantcontext is, bv. op `mijn.…`). Vang de Prisma
FK-/NOT NULL-fout generiek af naar een 400/409 in plaats van een 500.

## Status
**Opgelost** in WP-B3 (PR [#141](https://github.com/Enspezo/Inspexi-IPM/pull/141), branch `fix/wp-b3-superuser-scoping`).
Een SUPERUSER op een org-subdomein schrijft nu in de org van dat subdomein (effectieve org
via de `TenantGuard`, zie B-502); de kapotte create-paden (contacts, products, price-tables,
quote-templates, email-templates, product-groups, notification-groepsvoorkeuren) resolven de
org via `requireOrg(user)` en geven zonder orgcontext (bv. op `mijn.*`) een nette NL-400
"Selecteer eerst een organisatie". Vangnet in de exception-filter:
`PrismaClientValidationError` → 400 "Ongeldige gegevens" en `P2011` → 400, beide op
error-niveau gelogd mét requestId. E2e: `POST /contacts` als SUPERUSER met Host
`<org>.localhost` → 201 met de juiste `orgId`; op `mijn.localhost` → 400, nooit een 500.
