# B-505 — Geen gereserveerde-slug- of lengtecontrole: een organisatie met slug `mijn` (of 120 tekens) is aan te maken en daarna onbereikbaar

- **Testgeval:** SU-02 / SU-04 (verkennende uitbreiding)
- **Actor / rol:** Superuser / SUPERUSER
- **App:** API (:3001) `POST /organizations` · Portal (:5173)
- **Severity:** S3 (matig — onbruikbare organisatie, alleen te herstellen met een DB-ingreep; geen datalek)
- **Type:** grenswaarde / foutgok
- **Datum/tijd:** 2026-07-27 13:05

## Verwacht
De slug wordt het subdomein van de organisatie. Waarden die technisch of functioneel niet als subdomein
kunnen dienen — het gereserveerde superuser-subdomein (`mijn`, `SUPERUSER_SUBDOMAIN`), evenals waarden
langer dan een DNS-label (63 tekens) — horen bij het aanmaken geweigerd te worden met een NL-melding.

## Werkelijk
`CreateOrganizationDto.slug` kent maar één regel: `@Matches(/^[a-z0-9]+$/)`. Er is geen reserved-list,
geen minimum- en geen maximumlengte. Daardoor:

| Invoer | Resultaat | Gevolg |
|---|---|---|
| `mijn` | **201 Created** | `mijn.localhost` wordt door `TenantMiddleware.classifyHostname()` als *superuser*-domein afgehandeld vóórdat er een slug-lookup plaatsvindt. De organisatie staat in de lijst maar is via geen enkele URL te bereiken. |
| 120× `x` | **201 Created** | Langer dan een DNS-label (max 63); in productie nooit als subdomein te resolven. In de lijst duwt de slug bovendien de tabel uit beeld. |
| `a` (1 teken) | **201 Created** | Werkt wél (`http://a.localhost:5173` toont de org-branding). Toegestaan volgens de regex — genoteerd bij SU-02, geen bevinding op zich. |

Er is bovendien geen herstelpad in de UI: de slug is op de instellingenpagina read-only
("De slug kan niet worden gewijzigd") en organisaties kunnen niet verwijderd worden.

## Reproductie
```bash
TOK=<superuser accessToken>

curl -s -X POST -H 'Host: mijn.localhost' -H "Authorization: Bearer $TOK" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Gereserveerde Slug Test","slug":"mijn"}' \
  http://localhost:3001/api/v1/organizations
# → 201, "slug":"mijn"

curl -s -X POST -H 'Host: mijn.localhost' -H "Authorization: Bearer $TOK" \
  -H 'Content-Type: application/json' \
  -d "{\"name\":\"Lange Slug\",\"slug\":\"$(python3 -c 'print("x"*120)')\"}" \
  http://localhost:3001/api/v1/organizations
# → 201
```
Open daarna `http://mijn.localhost:5173` → nog steeds het SUPERUSER-portaal; de nieuwe organisatie
"Gereserveerde Slug Test" staat wél in **Organisaties**, maar heeft geen bereikbaar portaal.

## Bewijs
- HTTP 201 op beide creates (verwacht: 400 met NL-melding).
- `http://mijn.localhost:5173/organizations` toont beide rijen; het superuser-portaal blijft normaal
  functioneren (geen kaping — de middleware kortsluit vóór de lookup).
- Beide testorganisaties zijn na de verificatie weer uit de database verwijderd.

## Analyse / vermoedelijke oorzaak
`apps/api/src/modules/organizations/dto/create-organization.dto.ts`:
```ts
@IsString()
@Matches(/^[a-z0-9]+$/, { message: 'Slug mag alleen kleine letters en cijfers bevatten (geen streepjes)' })
slug: string;
```
`classifyHostname()` in `tenant.middleware.ts` vergelijkt het subdomein eerst met
`SUPERUSER_SUBDOMAIN` en doet pas daarna de org-lookup — een org met die slug is dus per definitie
onbereikbaar.

## Advies
- Voeg `@MinLength(2)` en `@MaxLength(63)` toe aan `slug`.
- Weiger een reserved-list: de waarde van `SUPERUSER_SUBDOMAIN` plus de gebruikelijke verdachten
  (`www`, `api`, `app`, `mail`, `admin`, `static`, `cdn`) met een NL-melding
  ("Deze slug is gereserveerd").
- Overweeg de slug muteerbaar te maken voor SUPERUSER (de API staat dit al toe, zie B-511 §2), zodat
  een verkeerd gekozen slug zonder DB-ingreep te corrigeren is.
